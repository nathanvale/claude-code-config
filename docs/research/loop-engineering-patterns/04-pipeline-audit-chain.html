The Pipeline Audit Chain

Chain specialist agents where each stage checks against the prior stage's output.

Cycle Mechanism

TL;DR

Arrange agents as an ordered audit chain — each stage validates the previous stage's output, not just the raw input. When a downstream agent finds a gap, it requeues the upstream stage. The loop terminates only when a full pass produces zero new findings.

How it works

Each stage holds a reference document — it audits relative to prior output, not raw input

The pipeline audit chain arranges agents in sequence, where each agent's job is to check the prior agent's output. Unlike a simple waterfall pipeline, this is a loop — when a downstream agent finds an issue, it requeues the upstream stage.

@PawelHuryn's four-stage pipeline is the clearest example in the dataset: document the app's intent first, then security-audit against that documented intent, then performance-audit against the security output, then derive tests against all of it. Each stage has a reference document to check against — not just "find problems", but "find problems relative to this prior output".

The code-review variant

@puccez228401's code-review loop is the same pattern applied to PRs: branch diff → reviewer profiles → verifier → fixer → re-review. The loop runs until the reviewers stop finding issues — at which point the PR opens automatically. The stop condition is measurable: zero new findings in a full pass.

Classify-and-act vs fan-out-and-synthesize

Anthropic describes two architectural variants for this pattern. Classify-and-act: one agent decides the category, the script routes to the right specialist. Fan-out-and-synthesize: all specialists run in parallel, results merged in code. Which to use depends on whether the stages are independent (fan-out) or sequential dependencies (classify-and-act).
