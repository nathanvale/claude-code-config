Harness > Prompt

You no longer prompt the agent. You design the system that prompts it for you.

Mechanism

TL;DR

The shift from prompting to loop engineering is a shift in what you are building: from messages to a system that generates messages. The prompt is 1/6th of the engineering. The harness is the other five sixths.

The 6 pieces of a loop

@alphabatcher's breakdown, building on Boris Cherny's model:

  • Automation — finds work on a schedule (GitHub issues, Slack messages, a queue)
  • Memory — CLAUDE.md, rules, prior run outputs
  • Skills — what the agent can do (slash commands, MCP tools)
  • Connectors — how the agent reads external systems
  • Sub-agents — specialists the orchestrator can delegate to
  • Verification — the stop condition that closes the loop

The prompt is one input to one of these six pieces. When you only write the prompt, you are doing 1/6th of the engineering. Loop engineering is the other five sixths.

@elvissun's claim

"We are at the point where you can solve ANY engineering problem by dropping an agent with the right harness in a loop." The emphasis is on "right harness" — not "any agent" or "any loop". The harness is the engineering. The agent is the execution engine.
