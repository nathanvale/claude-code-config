The pattern explained

The most important decision in loop design isn't the agent's prompt. It's whether the loop is bounded (runs until a goal is reached) or unbounded (runs perpetually on a schedule). These two types have completely different failure modes.

A bounded loop without a stop condition is a while(true) that burns your tokens. An unbounded loop without a schedule is just a one-shot run with extra steps.

Bounded loop

The loop terminates when a verifiable condition is true: tests pass, the PR opens, the output matches a spec, the stop_reason is end_turn. The stop condition must be external to the agent — the agent cannot be the one to decide it's done.

aso-agent "refactor auth module" --stop-when "all tests pass and no lint errors"

Unbounded loop

The loop runs on a schedule, reading from an external source (GitHub issues, Slack messages, a queue) to find its own work. The schedule is the stop condition — it runs, finishes its pass, and waits for the next trigger.

The failure modes

@Prathkum put it perfectly: "a loop that retries on failure is just a while(true) that burns your tokens." Retry-on-failure without a changed stop condition is not a loop — it's a spinner. The STOP signal is the rarest and most important design element in loop engineering.

TL;DR

Classify your loop before you build it. Bounded loops need an external verifiable stop condition — never agent self-report. Unbounded loops need a schedule and an external work queue. A loop without either is a token drain dressed as automation.
