The Harness Setup Recipe

Configure the agent's operating environment once. Then the loop does the prompting for you.

Mechanism
Setup sequence
Write CLAUDE.md
→
Add settings.json
→
Define verification step
→
Add skills / connectors
→
Loop runs the prompting
Stop: Setup is complete when the loop can operate without manual intervention

The harness is the infrastructure around the agent. Before you write a single prompt, you configure the environment the agent operates in — and that configuration is what makes the loop possible.

Boris Cherny, Claude Code's creator, summarises it: "My job is to write loops." The 5-day recipe from @alphabatcher operationalises what that means:

Day 1: Repo memory (CLAUDE.md)

# CLAUDE.md
Stack: TypeScript, Bun, React, Tailwind
Test command: bun test
Code style: no semicolons, single quotes
Release: conventional commits
Gotchas: never use git add -A

CLAUDE.md is the loop's long-term memory. Every run reads it. Everything the agent needs to know about the repo goes here — not in the prompt, here.

Day 2: Shell permissions (.claude/settings.json)

// .claude/settings.json
{
  "permissions": {
    "allow": ["Bash(bun test)", "Bash(git diff)", "Bash(git status)"]
  }
}

The agent needs to run tools. Which tools it can run without asking is a design decision — too restrictive and it interrupts constantly, too permissive and it can cause damage.

@0xSero's three harness rules

For iterative UI/system work: one task per prompt (don't stack requests), /new often to reset session boundaries, and the agent must remove more code than it adds (regression check). These three rules are a harness — they constrain the loop's behaviour without being in the prompt.

TL;DR

The harness is configured before the first prompt runs. Repo memory, shell permissions, verification steps, and skills are infrastructure — not prompt content. Get the harness right and the loop operates autonomously.
