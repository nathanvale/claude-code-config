Proving a Loop Works

A loop that only ever returns green is unfalsified, not validated. Prove the detector fires before you trust it.

Mechanism Validation

TL;DR

A self-auditing loop (Pattern 9) that keeps converging clean has proven nothing — a clean result is indistinguishable from a blind detector, and the stop rule rewards finding nothing. Before trusting any loop, prove its parts work against a known answer. Plant a known-positive and a near-miss negative, replicate the judgment across independent runs, and attack the design adversarially. Every proof method carries one trust condition — oracle, independence, adversarial, or falsifiability — or it is theater.

How It Works

→

→
Run it against a known answer
→

↺ accrue earned methods over loop parts
Trusted: each loop part has at least one earned proof method

In Practice

Pattern 9's stop condition — "no new contradictions in a full audit pass" — has a dangerous property: a detector that cannot see contradictions converges fastest and looks cleanest. Both are reported as "clean." A loop that has only ever run on healthy inputs is an instrument that has never deflected. You have not measured it; you have only failed to disturb it.

So validate the loop by its parts, not as a black box. An agentic loop decomposes into a handful of parts, each with a characteristic failure and a matching proof method:

The trust condition is the whole game

Every method names exactly one reason its result is believable. A test with no trust condition proves nothing, no matter how thorough it looks.

  • Oracle — the right answer was known in advance, so the result can be graded against ground truth.
  • Independence — separate judges reached the same result without sharing context.
  • Adversarial — someone was incentivized to break it and failed.
  • Falsifiability — there was a defined way the result could have failed; it did not.

The fixture pair is the core move

To prove a detector fires, you need a known answer. Plant one input with a known defect (the positive) and one that looks like a defect but resolves clean (the near-miss negative). A detector that accepts the positive and rejects the near-miss is discriminating — not just converging. The negative is what separates "the loop works" from "the loop says yes to everything."

For a prose judge, metamorphic relations beat oracles

An LLM judge often has no single correct output to check against. Instead, assert how the output should change when the input changes. Re-auditing an already-converged loop must add zero new findings — the relation (same input → same verdict) holds even though no "correct" finding count was ever known. This is how you prove a stop rule is a stable fixed point rather than a coin flip.

# A clean convergence proves nothing on its own.
# Plant a known defect and assert the loop catches it:
assert loop.audit(fixture_with_known_conflict).accepted == 1
assert loop.audit(near_miss_that_resolves_clean).accepted == 0

# Prove the stop rule is a fixed point, not luck:
assert loop.audit(already_converged_target).new_findings == 0

Earn methods; don't list them

A proof method earns its place only after it has been run against a real loop change at least once and produced a trust-condition-backed verdict — whether it caught a problem or confirmed clean. Speculative methods that sound good but were never run stay named slots, not trusted tools. The catalog grows by use, not by imagination — the same discipline Pattern 9 applies to contradictions, turned on the validator itself.

Why this is harder than it looks

The instinct, once a loop converges clean, is to run it on more inputs and trust the green. But scaling an unvalidated detector multiplies one ambiguity by N: a clean sweep over a whole library still cannot tell "everything is healthy" from "the detector is blind." Breadth is not proof. Only a known answer is.
