Architecture review

Skillport seam candidates

Skillport currently has a placeholder package only. This report names the seams to preserve before planning: skill operations first, the provider-supported agent target vocabulary in V1, clean adapter seams, no unrelated skill deletion, and agent-native observability.

solid box = module dashed edge = seam red = leakage risk dark box = deep module

MVP seam set

V1 must include: 1. Skills Provider, 2. Operation Planner / Executor, 3. Ownership Ledger, 4. Target Projection, and 5. CLI Facade front door. Ownership checks are an explicit MVP module, not hidden command behavior.

1. Deepen the Skills Provider module

MVP Strong

Files: proposed package modules; current placeholder has package.json and bin/skilldeck.js

Before

flowchart LR
  CLI[CLI commands] --> NPM[npx skills]
  Planner[Planner] --> NPM
  Doctor[Doctor] --> NPM
  Tests[Tests] --> NPM
  NPM -. leakage .-> Lock[skills-lock.json shape]
  NPM -. leakage .-> Fs[.agents/skills behavior]

After

flowchart LR
  CLI[CLI commands] --> Provider[Skills Provider module]
  Planner[Planner] --> Provider
  Doctor[Doctor] --> Provider
  Tests[Tests] --> Provider
  Provider --> Adapter[Npm Skills adapter]
  Provider --> Fake[Test fixture adapter]
Problem
Raw npx behavior leaks into every caller.
Solution
One provider interface hides source listing, install, remove, and status mechanics.
Wins
locality: backend swap is concentrated
leverage: one seam, many commands

2. Split Operation Planner from Operation Executor

MVP Strong

Files: proposed package modules; no current implementation

Before

Command decides target, mutates files, edits lock, and formats output.
Dry-run becomes a flag branch inside mutation code.

After

Planner
pure operations
->
Executor
requires execute
Problem
Safety rules disappear inside command branches.
Solution
Planner returns a mutation plan; Executor applies only explicit plans.
Wins
interface is test surface
locality: safety in one module

3. Deepen the Ownership Ledger module

MVP Strong

Files: future lock reader/writer module; consumes skills-lock.json shape

Before

flowchart TD
  Remove[remove command] --> Dir[skill dir exists?]
  Dir --> Delete[delete directory]
  Delete -. risk .-> Unrelated[unrelated local skill]

After

flowchart TD
  Remove[remove command] --> Ledger[Ownership Ledger module]
  Ledger --> Match{source + skill match?}
  Match -->|yes| Plan[remove-managed plan]
  Match -->|no| Refuse[structured refusal]
Problem
Directory existence is not ownership.
Solution
Ledger owns source identity, skill identity, and managed install facts.
Wins
unrelated skills preserved
leverage: every command checks ownership

4. Deepen Target Projection around provider target vocabulary

MVP Strong

Files: proposed target projection module; provider supports 50+ agent ids including claude-code, codex, and universal

Before

Commands hand-roll agent ids
Codex and Claude get special-cased
Future targets require command edits

After

flowchart LR
  CLI[Commands] --> Target[Target Projection module]
  Target --> Registry[Provider target registry]
  Registry --> Codex[codex]
  Registry --> Claude[claude-code]
  Registry --> All[50+ provider ids]
Problem
The wrapped provider already owns a broad agent vocabulary.
Solution
Target Projection validates and explains provider target ids without copying path rules.
Wins
locality: target meaning stays put
leverage: all provider ids exposed safely

5. Make the CLI Facade a front-door module

MVP Strong

Files: future command contract and runner modules; uses @side-quest/cli-command-facade

Before

flowchart TD
  Command[Command branch] --> Text[human text]
  Command --> Json[hand-built JSON]
  Command --> Errors[ad hoc errors]
  Command --> Hints[ad hoc repair hints]

After

flowchart TD
  Facade[CLI Facade module] --> Contract[command contract]
  Facade --> Help[rendered help]
  Facade --> Envelope[runtime envelope]
  Facade --> Station[station map proof]
Problem
Agents need parseable output and repair hints.
Solution
Facade front door owns discovery, help, envelopes, diagnostics, and continuations.
Wins
leverage: every command agent-native
locality: output rules in one module

6. Treat the Skillport skill as a later adapter

Speculative

Files: V2 skill package; V1 AGENTS.md route only

Before

Bootstrap depends on a skill that is not installed yet.

After

flowchart LR
  Agents[AGENTS.md route] --> CLI[Skillport CLI]
  Skill[Skillport skill later] --> CLI
  CLI --> Engine[deep engine modules]
Problem
A skill cannot bootstrap itself.
Solution
V1 uses AGENTS.md routing; V2 skill is an adapter over the CLI.
Wins
locality: workflow docs can evolve
interface stays CLI-first

Top recommendation

Start with all five MVP seams together

These modules create one safety loop. Provider hides the npm package dependency. Planner/Executor makes every mutation previewable before execution. Ownership Ledger proves what Skillport may touch. Target Projection exposes provider agent ids without forking that vocabulary. CLI Facade makes the loop agent-native.
