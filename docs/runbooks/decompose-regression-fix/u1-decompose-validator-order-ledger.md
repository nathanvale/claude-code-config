| 1 | issue-61-validator-order-hypothesis-refuted | closed | low | Issue #61 hypothesised that the 21 failing `decompose.test.ts` tests were caused by the `b.files.length === 0` validator firing before mode/id-shape/depends_on/supersedes/ac_mapping checks, and proposed reordering validators in `lib/ledger.ts`. Diagnosis showed the validator order is correct - the `has no files` error is the truthful first-violation report for those fixtures. The actual cause is upstream: `currentCommitFiles` is empty because HEAD (`7650a38`) is a merge commit and `git diff-tree --no-commit-id --name-only -r --root HEAD` returns nothing for merge commits without `-m`. | Closed: hypothesis refuted. The validator order in `lib/ledger.ts` was correctly NOT changed. The fix is in the test fixture initializer instead. |
| 2 | fix-approach-prefer-dash-m-flag-over-ls-tree | closed | low | Two viable approaches: (a) `git diff-tree -m` returns ~70 deduped files for the current merge commit and preserves "files touched in HEAD" semantics; (b) `git ls-tree -r` returns ~389 files (entire repo tree at HEAD) which always works but loses the "touched in HEAD" intent. Approach (a) preserves the contract that `oneBatchContractDigest`, `currentCommittedAttemptYaml(touched)`, and validator invariants depend on - the test digests hash a batch list that uses `currentCommitFiles` directly, and the batches' `builder_attempts.touched` must be a subset of the batch's `files`. | Closed: approach (a) selected. `-m` flag added to `git diff-tree`, result deduped via `[...new Set(...)]`. Approach (b) deferred indefinitely. |
| 3 | merge-commit-empty-files-currentcommitfiles | fixed | low | The `currentCommitFiles` initializer in both `runbooks/issue-to-pr-v2/decompose.test.ts` and `runbooks/issue-to-pr/decompose.test.ts` shells out to `git diff-tree --no-commit-id --name-only -r --root HEAD` at module-load time. For a merge-commit HEAD (current main: `7650a38`, merge of PR #59), that command returns nothing. The 21 test fixtures that interpolate `currentCommitFiles` then have empty `files:` arrays, which legitimately trips the `b.files.length === 0` validator and preempts the specific assertions those tests want to make. | Fixed: added `-m` flag to `git diff-tree` and wrapped the result in `[...new Set(...)]` for dedup. Applied byte-for-byte to both v1 and v2 mirrors per U3's parity contract. |
| 4 | merge-commit-empty-currentcommittouchedfiles | fixed | low | `currentCommittedAttemptYaml(...)` defaulted `files_touched` to `currentCommitFiles`, but the in-lib `touchedFilesForCommit` validator derives the expected set using `git diff-tree --no-commit-id --name-status -r --root -M ref` (no `-m`). After fix-3 made `currentCommitFiles` non-empty via `-m`, the persisted `files_touched` was non-empty while the validator-derived set was still empty (merge-commit HEAD), producing a fresh "files_touched does not match git diff" failure in tests that previously passed. | Fixed: introduced a parallel `currentCommitTouchedFiles` constant that mirrors the validator's exact git command (no `-m`, with `-M`, with name-status parsing). Made `currentCommittedAttemptYaml`'s default `files` reference the new constant so persisted and derived sets agree. |
| 5 | mismatched-files-fixture-no-longer-mismatched | fixed | low | The `validates committed builder attempts against commits and touched files` test built a sub-fixture (`mismatched-files.md`) that set `files: []` for the persisted `files_touched`, expecting the validator's `sameStringSet` check to fire because the derived set was non-empty on non-merge HEADs. With merge-commit HEAD, the validator-derived set is also empty, so `sameStringSet([], [])` is true and the test fails. | Fixed: changed the per-test override from `files: []` to `files: [currentCommitFile]` (a proper subset of the batch's allowed files but never equal to the validator-derived set on either merge or non-merge HEADs). Approved per-test fixture body edit, scope expanded by row 6. |
| 6 | outsidebatchfiles-fixture-files-touched-now-empty | fixed | low | Sibling sub-fixture (`outside-batch-files.md`) in the same test constrained the batch to `files: ["README.md"]` and relied on `currentCommittedAttemptYaml(..., { commitSha: currentCommit })` defaulting `files_touched` to the multi-file batch-files list, which (pre-merge-commit) produced an "unauthorized" mismatch. After fix-4, `files_touched` defaults to the empty `currentCommitTouchedFiles` on merge HEAD, which is trivially a subset of `["README.md"]` and never trips the validator. | Fixed: chained an explicit per-test override that supplies `files: [currentCommitFile]` (which is `bun.lock` for `currentCommit = 7650a38`, definitely outside `["README.md"]`). The validator's `unauthorized` check now fires on both merge and non-merge HEADs. |
