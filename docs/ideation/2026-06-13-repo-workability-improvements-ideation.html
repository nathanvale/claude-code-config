Ideation: Repo Workability Improvements

Improvement ideas drawn from the recent workability pass over this repo: strong owner maps and contracts, but high orchestration load when an agent needs to know the next safe action.

date: 2026-06-13 topic: repo-workability-improvements focus: improvement ideas from workability report mode: repo-grounded

Grounding Context

Core philosophy

AGENTS.md says deterministic contracts belong in code, generated docs, CLI help, or checks. Skills route workflows; owner paths own behavior.

Observed friction

A real run needed tests, hook tests, typecheck, Biome, Fallow, decision logging, plan checkboxes, YAML parsing, startup checks, and skill-feedback closeout.

Known sharp edge

scripts/agent-instructions.sh check printed Agent instruction health: ok, then exited through an unbound failures[@] array bug.

Existing assets

test-runner, create-cli, fallow, and skill-feedback already point toward compact output, command contracts, and action metadata.

Recent ideation

Recent docs favor benchmark-gated runner proof, thin skill prose, per-finding resolver actions, and review results that distinguish evidence from claims.

External context

Broad agentic-development research reinforces the risk: agent workflows add overhead when setup, check selection, and repair paths are not integrated.

Ranked Ideas

1

Task Doctor

Description: Add one repo-local command that reads the current diff, recent plan, touched owner paths, known skill rules, and ignored evidence folders, then emits the next safe check bundle. The output is not a generic CI list; it is a task-local route: focused tests, typecheck, lint, doc parse, startup health, Fallow, skill-feedback closeout, and known caveats.

Axis: Check orchestration Confidence: 90% Complexity: Medium

Basis: direct: AGENTS.md requires several post-change rituals, while test-runner, context/bun-runner.md, create-cli, fallow, and skill-feedback each own part of the gate. The last task proved the cognitive load: the right checks existed, but the agent had to assemble the route manually.

Rationale: This is the biggest leverage move because it turns repo philosophy into one inspectable runtime answer: what should I run now, and why? It reduces missed rituals without copying every rule into startup prose.

Downsides: Needs careful scope control. If it grows into a universal orchestrator, it becomes the bloat it was meant to remove.

2

Command Surface Map

Description: Generate a repo-local index of skill CLIs and command surfaces: command name, owner path, side-effect stance, help command, result contract when present, and proof files. The map should be machine-readable first and readable in plain text second.

Axis: Command discovery Confidence: 86% Complexity: Medium

Basis: direct: create-cli requires naming contract, model, engine, discovery, CLI, and test owners. skill-feedback has a command-surface proof section naming discovery metadata, rendered help, argv accept/reject, and runtime semantics.

Rationale: The repo is good at building agent-native commands one at a time. A map would let fresh agents discover those surfaces without rereading every skill. It also gives Task Doctor a stable input.

Downsides: If hand-authored, it will drift. It should be generated from command contracts, package scripts, and owner sections, with docs only as fallback.

3

Current Task Skill-Feedback Review

Description: Add a scoped review mode for skill-feedback that answers: what did this task produce, what closeouts apply, what low-signal capture happened, and what open evidence is relevant to the current touched surfaces? Scope could be by time window, touched path list, or an explicit run id once trusted correlation exists.

Axis: Feedback and learning loop Confidence: 84% Complexity: Medium

Basis: direct: the last implementation filed a closeout to .skill-feedback/, but the review model is inbox-wide. The new inbox_health and low-signal lane make global review safer, but not necessarily easier for a task closeout.

Rationale: The feedback loop becomes much more usable when an agent can ask for this task's learning signal rather than inspecting the whole private inbox. It also turns closeout from a ritual into something visibly useful.

Downsides: True run scoping needs trusted correlation that does not exist yet. A v1 should avoid overclaiming and use path/time filters with clear caveats.

4

Decision Log Appender

Description: Add a helper that finds the right decision surface, computes the next sequenced id, validates YAML, and appends a decision entry from a compact structured input. It should support dry-run and execute, with a preview diff.

Axis: Governance navigation Confidence: 82% Complexity: Low-Medium

Basis: direct: record-decision says to append one fenced YAML decision entry and run the checker when available. In the last task, the accepted decision flow was correct but manual: choose log, number id, format YAML, and avoid copying deterministic contracts.

Rationale: Decisions are high-value but currently fiddly. A small appender would reduce YAML and numbering mistakes while keeping the durable prose shape intact.

Downsides: It must not become an ADR generator or decision-maker. It records accepted decisions only.

5

Fallow Noise Profile

Description: Teach Fallow about this repo's expected noise zones: integration-heavy CLI tests, facade contract exports, and helper seams that are covered through runner-level tests rather than direct unit tests. The output should separate actionable introduced findings from known-shape noise with a reason.

Axis: Analyzer noise and review triage Confidence: 78% Complexity: Medium

Basis: direct: Fallow reported 25 introduced findings on the recent task, but sampled items were mostly test duplication and integration seam coverage. Recent Fallow ideation already points toward per-finding resolver actions and attribution gates.

Rationale: Fallow is useful, but its current output still makes agents do human triage. A repo profile would turn "issues found" into "issues worth attention" without suppressing evidence globally.

Downsides: Suppression can hide real problems if too broad. The profile should explain each downgrade and keep a raw count visible.

6

Workability Pulse

Description: Produce a periodic or on-demand report that ranks the repo's current agent-work friction from real signals: failed checks, Fallow triage, skill-feedback closeouts, broken owner checks, repeated decision-log edits, and plan checkbox churn.

Axis: Feedback and learning loop Confidence: 72% Complexity: Medium-High

Basis: reasoned: this repo already captures many evidence streams, but each is local to its workflow. A pulse would compound them into prioritization, making the next improvement obvious rather than anecdotal.

Rationale: This is the strategic version of Task Doctor: instead of helping one turn finish, it helps the repo decide what to improve next.

Downsides: Needs enough signal volume and careful privacy boundaries. It is less urgent than fixing the immediate task-level routing pain.
