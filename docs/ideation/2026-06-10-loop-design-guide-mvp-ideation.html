Ideation: Loop Design Guide MVP

MVP options for a skill and prompt-pack surface that helps Codex and Claude agents design stronger agentic loops. The direction stays Use mode first, treats examples as references rather than recipes, and adds only enough lifecycle scaffolding to keep future curation safe.

Grounding Context

Codebase Context

  • Repo is Nathan's user-scope agent configuration for rules, context, skills, agents, commands, hooks, scripts, runtime surfaces, and research docs.
  • Repo rules favor thin skills, one workflow per skill, explicit owner paths, maps, invariants, next safe actions, and inspectable state.
  • Skill authoring guidance says deep workflow mechanics belong in references, while the skill body routes request shape and names next safe action.
  • skills/mvp-loop-maker/SKILL.md already covers reviewer findings-ledger loops. The new MVP should design loops, not dispatch reviewers or claim convergence.

Past Learnings

  • Build prompt packs from ledgers, not loose examples. Keep source, loop type, signal labels, qualification reason, and lifecycle state together.
  • Keep the MVP prose/reference-first unless runtime behavior is earned by parsed input, machine-readable output, durable writes, or repair semantics.
  • Use lifecycle vocabulary from existing repo patterns: candidate, accepted, active, demoted, retired.
  • Keep prompt packs out of startup/control-plane prose. Skills and references should own workflow depth.

External Context

  • Prior art reinforces loop design as guides plus sensors: closed-loop verification, maker/checker splits, circuit breakers, and human-on-the-loop steering.
  • Prompt lifecycle practice points toward versioned prompts, golden datasets, promotion gates, active-learning example selection, stale-example retirement, and model-registry style lineage.
  • Risks to design around: runaway loops, stale examples, label noise, overfitting to examples, silent failure compounding, and false safety from one-layer guardrails.

I1.

Loop Card As Promotion Seed

Confidence 88% Complexity Medium
Description
Make Use mode output one compact loop card that also becomes the seed for future curation. The card captures goal, cycle, stop signal, verifier, evidence plan, human checkpoint, loaded context, assumptions, missing context, owner paths, and rollback or demotion path.
Axis
Use-mode loop design guidance.
Basis
direct: the handoff names the compact loop card as the default output and says success loops can become prompt-pack promotion candidates.
Rationale
One artifact compounds. It improves the loop before an agent runs it, then preserves the exact evidence future curation would need without requiring a second capture workflow.
Downsides
The card can become too wide if every future lifecycle concern is pulled into v1. The MVP needs a hard distinction between fields needed for loop design and fields only useful after a run completes.
I2.

Signal Identification Key

Confidence 86% Complexity Low
Description
Turn CYCLE, STOP, MECHANISM, and EVIDENCE into the skill's diagnostic key. The agent first identifies which signals the proposed loop has and which are missing, then improves the card only around the missing signals.
Axis
Use-mode loop design guidance.
Basis
direct: the mined corpus uses these four labels, with STOP repeatedly called out as the common omission and EVIDENCE as rare and high-value.
Rationale
The signal key makes the guide concrete. It avoids a generic loop-design essay and gives agents a repeatable inspection step before they suggest loop mechanics.
Downsides
The labels can become checklist theater if the skill accepts shallow answers. The guide needs examples of strong and weak signal evidence, especially for STOP and EVIDENCE.
I3.

Signal-Gated Example Ledger

Confidence 84% Complexity Medium
Description
Replace the static prompt-pack excerpt with a small curated ledger. Each entry records source path or URL, loop type, signal labels, qualification reason, lifecycle state, and whether it is active, candidate, demoted, or retired.
Axis
Curated example / prompt-pack shape.
Basis
direct: the existing ledger has signal-scored examples, but the handoff says the current prompt pack is static and not lifecycle-managed.
Rationale
A ledger makes future curation inspectable. It also lets Use mode load narrow examples by signal fit instead of dragging the whole corpus into context.
Downsides
A ledger creates maintenance expectations. If the MVP cannot name who owns it and when it changes, it becomes another stale source next to the existing excerpts.
I4.

Reference Picker, Not Recipe Picker

Confidence 82% Complexity Medium
Description
In Use mode, select one to three examples by missing signal and loop type, then ask the agent to extract design questions from them. The selected examples should influence the card by raising questions, not by copying their shape.
Axis
Curated example / prompt-pack shape.
Basis
direct: the handoff says examples are references, not recipes, and the audit says to load narrow context rather than the full pack by default.
Rationale
This protects the pack from becoming a cargo-cult cookbook. It also makes the examples useful earlier, before the curation system is mature.
Downsides
The picker may feel weaker than a concrete prompt template. The skill must make the design-question extraction crisp enough that agents can actually use it.
I5.

Lifecycle Without Mutation

Confidence 80% Complexity Medium
Description
Give v1 lifecycle language without giving it active-pack authority. Use mode may produce candidate, promotion_candidate, and demotion_evidence records, but it does not mutate the active prompt pack without explicit human confirmation.
Axis
Lifecycle state and evidence records.
Basis
direct: the handoff requires human confirmation for promotion or demotion and says bad accepted improvements can create demotion evidence. external: prompt lifecycle and model-registry patterns use explicit promotion gates and retirement states.
Rationale
This is the minimum curation scaffold that keeps future work safe. It avoids the two bad extremes: no lifecycle at all, or a full curate engine in the first slice.
Downsides
Lifecycle labels can imply more machinery than exists. The MVP needs plain wording that these records are evidence for later decisions, not automatic decisions.
I6.

Human Retro Microform

Confidence 78% Complexity Low
Description
Add a tiny post-run retro block: goal completed, stop signal worked, evidence inspected, improvement accepted, harmful behavior noticed, promote candidate yes/no/unsure. Keep it as questions the agent can ask after a loop card is used.
Axis
Human retro and improvement acceptance.
Basis
direct: the handoff says promotion requires goal completion, human retro feedback, and accepted improvements, and asks for the minimum viable retro questionnaire.
Rationale
The microform turns human judgment into curation evidence while keeping curation outside the first interaction. It also defines what "loop agrees to implement improvements" means: a named change accepted by the human after evidence review.
Downsides
Retros add friction. The skill should make the microform optional after design-only use, but required before any promotion candidate is recorded.
I7.

Authority Circuit Breaker

Confidence 76% Complexity Medium
Description
Every loop card names what the agent may change, what needs confirmation, what interrupts the loop, where evidence is written, and which owner paths control cards, examples, retros, promotion records, demotion records, improvements, and the active pack.
Axis
Safety boundaries and owner paths.
Basis
direct: repo rules require owners, next safe actions, and inspectable state; the audit findings ask for shared owner paths and read-before-write behavior. external: circuit-breaker and prompt-lifecycle practices use explicit gates to prevent runaway or unsafe promotion.
Rationale
This keeps the guide from implying unattended autonomy without interruption paths. It also prevents future lifecycle records from scattering across the repo.
Downsides
Owner mapping may slow the first-use experience. The MVP should default owner paths only where the repo already has a clear convention and otherwise stop at a proposed path map.

Rejection Summary

# Idea Reason Rejected
1 Design Guide, Not Loop Runner Kept as an MVP boundary, but too thin as a standalone product direction.
2 Evidence Budget Over Feature Budget Merged into I1 and I2; evidence is a required card field and signal, not a separate MVP.
3 Evidence Plan As Default Field Merged into I1; useful field, not enough product shape alone.
4 Owner Paths Before Actions Merged into I7; the stronger framing is the authority boundary plus owner map.
5 Demotion Evidence From Day One Merged into I5; demotion evidence is necessary lifecycle scaffolding, not its own MVP.
6 Accepted Improvement Watchlist Merged into I6; valuable but better expressed through the retro microform.
7 No Curate Mode Yet Merged into I5; it is a constraint on lifecycle authority, not a feature.
8 Remove Runtime CLI From MVP Accepted as a scope boundary. Too implementation-shaped for the ideation survivor set.
9 Zero Lifecycle Use-Only MVP Too unsafe for future curation; it would make promotion and demotion expensive to retrofit.
10 Full Curate Engine Too expensive for MVP and violates the Use mode first constraint.
11 Auto-Promotion Rejected for safety. The handoff requires explicit human confirmation before prompt-pack mutation.
