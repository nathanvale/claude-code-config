Ideation: Skill Feedback MVP and Actionability

The original MVP created the missing human surfaces. The 2026-07-24 extension asks how Variant B can turn observed activity into one safe, evidence-backed decision.

Grounding Context

Current architecture defines `skill-feedback` as a CLI over repo-local Software Learning Reports, but the public command surface is `record`, `closeout`, `dashboard`, `review`, `health`, `purge`, and `correlate`. That surface exposes capture and diagnostics before it exposes the reports themselves.

The inbox scanner already reads safe JSON files, normalizes reports, splits primary from low-signal reports, and preserves invalid or unsafe artifacts as evidence. The data needed for a report browser exists; the missing piece is a human product surface over it.

Live health output on 2026-07-01 showed `primary=254`, `low_signal=545`, `unlinked_primary=254`, and `next_action=preview-correlation-repair`. That next action is technically coherent but product-wrong for a human trying to inspect learning reports.

Direct repo basis: `skills/skill-feedback/ARCHITECTURE.md:7` describes the CLI over reports; `ARCHITECTURE.md:104` lists the current command surface; `skills/skill-feedback/src/inbox-read-model.ts:180` reads normalized inbox reports; `skills/skill-feedback/src/decision-surface.ts:135` routes blocked witnesses to correlation preview; `skills/skill-feedback/src/skill-feedback-runner.ts:1436` says plain review is bounded and agent-scanning oriented.

1 Reports First: `skill-feedback reports`

Make `reports` the first MVP command. It prints a bounded, readable table of recent reports with timestamp, skill, outcome, one-line goal, lane, and `report:<id>`. It defaults to recent primary reports and accepts small filters like `--skill`, `--source`, `--lane`, and `--limit`.

Axis
Report access
Basis
direct: `ARCHITECTURE.md:7-18` says the product is a CLI over Software Learning Reports, but `ARCHITECTURE.md:104-112` lists no command that simply shows reports. Current health output proves there are hundreds of reports to show.
Rationale
This is the missing product doorway. Without it, every other analytic surface feels fake because users cannot inspect the evidence.
Downsides
Requires a stable plain layout and output budget. Needs careful default sorting so low-signal noise does not drown primary reports.
Confidence: 95% Complexity: Medium

2 Report Detail: `skill-feedback report <id>`

Add one drill-down command that resolves `report:<id>` to a human-readable report page. Show goal, friction, verification burden, touched surfaces, observations, evidence gaps, source, lane, and generated time. Keep `--json` for scripts, but make plain text the default.

Axis
Report access
Basis
direct: review output already emits `report:<id>` evidence refs, and `inbox-read-model.ts:180-230` already returns normalized report objects split by primary and low-signal lanes.
Rationale
`report:<id>` currently points to an internal lookup ritual. This command closes the loop from signal to evidence.
Downsides
Duplicate report IDs and invalid reports need clear errors. The command should avoid exposing unsafe filesystem paths by default.
Confidence: 93% Complexity: Medium

3 Usage Board: `skill-feedback usage`

Rank skills by report count, confirmed/failed/ambiguous outcomes, closeout coverage, low-signal volume, last seen time, common friction, and common verification burden. The command answers one question: which skills are actually being used and how healthy are they?

Axis
Skill usage
Basis
direct: reports carry `skill`, `outcome`, friction, verification burden, source, and generated timestamp; current sample rows include recent `skill-feedback`, `skill-author`, `handoff`, and `compound-engineering:ce-commit` reports.
Rationale
Continuous improvement needs usage distribution before deep diagnostics. This turns passive capture into a portfolio view.
Downsides
Unknown-skill and low-signal reports can distort rankings unless the lane is visible and filterable.
Confidence: 88% Complexity: Medium

4 Improvement Queue: `skill-feedback queue`

Convert repeated evidence into a ranked queue of improvement candidates. Rows show target skill or owner path, reason, supporting report refs, observed friction, verification burden, and the next safe action. The first version can use existing review ledger data without adding new report fields.

Axis
Improvement queue
Basis
direct: current `review --plain` already produces engineering signals and open actions with owner paths and `report:<id>` refs, but the output is long, truncated, and mixed with health, readiness, witnesses, and ledger internals.
Rationale
This is the actual continuous-improvement loop. It changes the product from "we stored reports" to "here is what to fix next."
Downsides
Ranking can imply false certainty. The command should label evidence strength and allow `--skill` and `--owner` filters.
Confidence: 84% Complexity: Medium

5 Default Dashboard as Command Launcher

Rewrite zero-arg `skill-feedback` as a small command launcher with counts, newest report time, top used skills, top friction, and exactly four commands: `reports`, `report <id>`, `usage`, and `queue`. Diagnostics move behind `health`, `review`, and `correlate`.

Axis
Default path
Basis
direct: `decision-surface.ts:135-139` currently chooses `preview-correlation-repair`; the live dashboard followed that path even when the user wanted to see reports.
Rationale
The first command teaches the product. If it points to internal repair, the product feels broken even when data exists.
Downsides
Requires changing tests that currently assert correlation and purge next actions on the dashboard.
Confidence: 91% Complexity: Low

6 Weekly Skill Learning Digest

Add a read-only digest command after the first four surfaces exist. It summarizes the last 7 days: most-used skills, new friction, highest verification burden, repeated owner paths, and suggested follow-up. It gives the system a recurring review ritual without requiring the user to remember individual commands.

Axis

Basis

Rationale
This makes the skill observability loop durable. It also helps identify unused skills by absence, not just noisy skills by report count.
Downsides
Not MVP-zero. It depends on report browsing and usage ranking first, otherwise it becomes another opaque summary.

Rejection Summary

# Idea Reason Rejected
1 Fix correlation first Wrong MVP order. Correlation improves trust, but report visibility is blocked at the product layer.
2 Build a rich web UI Too expensive before the CLI answers basic questions. Start with commands that can later power a UI.
3 Make `review --plain` bigger Duplicates the current failure mode: one dense mixed output instead of task-specific human commands.
4 Auto-edit skills from evidence Too much agency for evidence-only reports. The MVP should recommend edits and preserve human review.
5 Purge and retention tooling Operationally useful, but it does not help users understand report value.
6 Trusted Codex identity Blocked on engine-owned evidence. Keep it visible in health, but do not let it block human observability.

MVP Cut

Ship `reports`, `report <id>`, `usage`, `queue`, and the default dashboard rewrite. Defer correlation repair, purge parity, rich UI, and automated skill edits.

Acceptance bar: a fresh user can run `skill-feedback`, pick one of the shown commands, inspect actual reports, see which skills are used, and get a ranked improvement queue without touching `jq`, filenames, or report schemas.

Actionability extension · 2026-07-24

Variant B: From Activity Runway to Safe Decision

The original rejection of a rich web UI was an ordering decision, not a permanent constraint. The CLI now has reports, report detail, usage, and queue contracts. Variant B can build on those foundations without inventing a skill-quality score or editing reports.

Top direction: keep the runway as the entry point. A click on a primary signal opens Single-Case Review Mode. That mode presents an Actionability Brief, resolves the queue for the focused skill, offers one next safe inspection, then closes through source-change handoff, no-build, or a named blocker.

Grounding

  • Variant B currently moves from a run or skill click to filtering, then from a report click to a compact drawer. It does not yet complete an evidence-to-decision loop.
  • Low-signal reports prove capture activity. They do not prove skill attribution or poor skill performance, so they need a subordinate capture-health lane.
  • Report detail already owns touched surfaces, observations, evidence gaps, and provenance. Queue already owns reason, evidence refs, next safe action, and no-build.
  • A broad recent-reports payload and a broad top-queue payload often do not intersect. Resolve queue evidence after the user focuses a skill.
  • The trustworthy product loop is observe, focus, inspect evidence, confirm the owner source, then change, no-build, or block.
  1. Observe
  2. Focus one signal
  3. Inspect evidence
  4. Confirm owner source
  5. Choose an exit
  6. Change, stop, or block

Topic Axes

Signal qualification
Separate inspection-worthy primary evidence from capture-health volume.
Evidence chain
Keep every conclusion traceable to reports, observations, gaps, and provenance.
Safe continuation
Offer one bounded next read only when the existing contract supports it.
Decision closure
Make change, no-build, and blocker outcomes explicit and credible.

A1 Single-Case Review Mode

A focused run, skill, or primary report temporarily turns the runway into one case file. Keep the activity context visible, but centre the evidence chain, uncertainty, safe continuation, and closure for that one case.

Recommended Prototype Cut

Prototype one vertical slice: B runway → primary signal → Single-Case Review Mode → Actionability Brief → queue-on-demand → one next safe inspection → change handoff, no-build, or blocker.

Keep low-signal as a compact capture-health rail. Stop before source edits, patches, agent invocation, persistence, or a synthetic skill score. Measure time to safe inspection and whether users can reach a credible no-action decision.
