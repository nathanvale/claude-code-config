Bad Practices Skill: Strengths, Weaknesses, Improvement Ideas

A repo-grounded critique of skills/bad-practices, with external research on AI-generated code smells, agent coding guidelines, and test-suite health.

date: 2026-06-15 topic: bad-practices-skill focus: external-research skill improvement mode: repo-grounded

Grounding Context

The current skill is a thin knowledge bank and translation layer. It routes architecture, testing, CLI, and agent-workflow smells toward existing owners instead of trying to become the owner. That is the right starting posture for a skill meant to reduce AI-slop without creating a second policy system.

External research supports the need for this kind of bank. A 2026 arXiv paper on AI-generated smells reports that functionally correct agent output can still accumulate structural and architectural debt, including long methods, god-class tendencies, unstable dependencies, and superficial modularity. Stack Overflow's 2026 guidance on agent coding standards argues for explicit repo conventions, correct and incorrect examples, gold-standard examples, and failure-driven updates to standards. Google Testing Blog and Fowler both reinforce the testing side: flaky and overly high-level suites erode trust, slow feedback, and need deterministic handling rather than hand-waving.

Strengths

  • Thin wrapper shape keeps ownership clear.
  • Architecture and testing references stay one level down.
  • Entry shape includes bad practice, failure mode, better substitute, evidence class, and downstream skill.
  • Owner paths point to ICA, seam-scaffold, GoF pressure, cli-author, and test-runner instead of copying their contracts.
  • Positive-substitute framing avoids pure complaint taxonomy.

Weaknesses

  • No lifecycle for candidate, observed, and promoted entries.
  • No promotion rule from skill-feedback or review findings into the catalog.
  • No dedicated agent-workflow or CLI/runtime bad-practice domain yet.
  • No packet template for seam-scaffold or future review skill handoff.
  • No catalog lint to catch missing fields, duplicate smells, or unowned owner-path labels.

Source Signals

  • AI-Generated Smells: functional correctness can hide maintainability debt; prompt detail alone does not remove architectural decay.
  • Stack Overflow agent guidelines: predictable standards, examples, and failure-fed updates improve agent output.
  • Google Testing Blog on flaky tests: flaky results create false alarms, delayed signal, quarantine tradeoffs, and ignored real failures.
  • Fowler test pyramid: too many high-level tests create slow, brittle, non-deterministic suites; lower-level tests carry most coverage.

1. Evidence Ladder and Feedback Intake

Add entry maturity labels such as candidate, observed, and promoted, plus a short intake rule: only add a catalog entry when there is a local failure, external evidence, or repeated review pattern. Connect material skill-feedback reports to this intake path.

Axis: Evidence Lifecycle

Basis: external: Stack Overflow frames agent errors as feedback for standards; direct: the current catalog already has evidence classes but no lifecycle.

Rationale: This prevents the catalog from becoming a grumble bucket. It also gives the future scaffold or review skill a clear threshold for promoting a smell into executable checks.

Downsides: Adds small taxonomy overhead. Requires discipline when adding entries.

confidence 88% complexity Medium

2. Bad-Practice Handoff Packet

Add a compact packet template for downstream use: smell, trigger, local evidence, external evidence, better substitute, owner path, candidate downstream skill, promotion threshold, and next safe action. Use it when the skill is asked to prepare seam-scaffold, review, or plan improvements.

Axis: Handoff Shape

Basis: direct: current output shape is close but not packaged for downstream adoption; external: agent guidelines benefit from predictable, repeated shapes and examples.

Rationale: The packet turns a passive knowledge bank into a clean feeder for future scaffolding and review work without making this skill the executor.

Downsides: Slightly more ceremony for one-off lookups.

confidence 84% complexity Low

3. Agent-Workflow Bad-Practice Domain

Add references/agent-workflow.md for agent-specific slop patterns: instruction bloat, unowned contracts, prompt-only quality gates, broad refactors, silent fallback, skipped source reading, fake determinism, and over-patterned architecture.

Axis: Domain Coverage

Basis: external: AI-generated smell research argues that agent output needs architectural foresight; direct: repo instructions already name agent-native principles, owner maps, next safe actions, and inspectable state.

Rationale: This domain aims directly at the user's "minimum AI slop" goal. It also captures failure modes that are neither pure architecture nor pure testing.

Downsides: High risk of vague taste-policing unless entries require evidence and a positive substitute.

confidence 82% complexity Medium

4. Testing Determinism Lens

Expand testing entries with a determinism and pyramid lens: global state, time, randomness, external services, cwd mutation, retry masking, quarantine masking, over-broad UI/e2e tests, and missing low-level contract tests.

Axis: Domain Coverage

Basis: external: Google reports flaky tests as same-code pass/fail signals with costly workflow impact; Fowler warns that too many UI-level tests are slow, brittle, and non-deterministic.

Rationale: The current testing catalog is useful but mostly local-harness shaped. This lens gives it a larger quality model while preserving repo-local ownership.

Downsides: Needs careful wording so it does not become "never write integration tests".

confidence 80% complexity Medium

5. CLI and Runtime Bad-Practice Domain

Add references/cli-runtime.md for command-surface smells: help/parser drift, prose-only schemas, stdout-as-contract without JSON, non-interactive command prompts, exit-code-only tests, wrapper-output assertions, and missing repair hints.

Axis: Domain Coverage

Basis: direct: repo startup instructions route CLI contracts to cli-author; current testing entries already include wrapper-output and exit-code-only smells.

Rationale: CLI/runtime surfaces are where agent workflows become mechanical. A bad-practice catalog that misses this layer leaves review and scaffold work underpowered.

Downsides: Some entries may belong in cli-author instead; the skill needs owner-first wording.

confidence 78% complexity Medium

6. Catalog Lint

Add a small validation script later, after the entry shape stabilizes. It can check required fields, duplicate headings, malformed evidence classes, stale local paths, and owner labels that are not declared as local or external.

Axis: Mechanical Validation

Basis: external: Stack Overflow's agent-guideline article still keeps linters and static analysis in the build pipeline; direct: the repo already uses checks for YAML and skill metadata.

Rationale: A knowledge bank about bad practices should not quietly accumulate its own bad-practice shape. Mechanical checks let prose stay thin.

Downsides: Premature if built before the catalog has 20-30 entries across domains.

confidence 74% complexity Medium

7. Example Pairs and Gold Entry

Add one correct and incorrect mini-example per domain, plus a single "gold entry" that demonstrates the intended catalog shape. Keep examples short and local to the reference file that owns the domain.

Axis: Agent Ergonomics

Basis: external: Stack Overflow recommends correct and incorrect examples, plus a gold-standard example, because agents follow patterns well.

Rationale: The current entry shape is clear to a careful reader, but examples will make it harder for future agents to add vague or unowned entries.

Downsides: Examples can rot. They need to remain tiny and tied to the same owner-map discipline.

confidence 76% complexity Low

Rejection Summary

# Idea Reason Rejected
1 Turn bad-practices into a full review skill now Premature. The bank needs observed entries, promotion rules, and packet shape before it can review reliably.
2 Move bad-practice rules into startup instructions Conflicts with repo guidance that skills own workflows and startup instructions stay hard rules and routes.
3 Copy ICA, DDD, GoF, cli-author, or test-runner contracts into this skill Duplicates owner contracts and creates drift. The skill should link owners and translate smell packets.
4 Import a universal code-smell taxonomy wholesale Too broad for a repo-local skill. External terms help, but entries need local owner paths and positive substitutes.
5 Ban high-level tests Wrong lesson from the test pyramid. Prefer fewer, purposeful high-level tests and stronger lower-level contracts.
6 Auto-fix bad practices directly from the catalog Too much agency before evidence maturity. Use the catalog for routing, scaffold packets, and review prompts first.
7 Rename the skill immediately The user-named trigger is direct and memorable. Improve evidence and substitution discipline before revisiting naming.
