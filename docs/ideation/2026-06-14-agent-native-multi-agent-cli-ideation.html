Ideation: Agent-Native Multi-Agent CLI

A fresh product pass on a new CLI for multi-agent development in this repo. The premise: use SideQuest as source material, but build a proper agent-native command contract from the start, with worktree as the front door.

Date: 2026-06-14 Topic: agent-native-multi-agent-cli Mode: repo-grounded Raw ideas: 47 Survivors: 7

Grounding Context

Repo doctrine: AGENTS.md says agent-native work should give maps, invariants, owners, next safe actions, inspectable state, mechanical CLI surfaces, continuations, repair hints, and failures that expose cause plus repair path.

Existing front door: skills/worktree already proves the pattern: a thin skill points to owner files, a facade-backed command contract owns discovery/help/runtime behavior, and the CLI delegates worktree CRUD instead of duplicating it.

SideQuest carry-over: SideQuest has useful worktree lifecycle logic: create, list, check, delete, clean, recover, sync, status, orphan branch detection, dry-run cleanup, backup refs, and health metadata. Its product gap is not the logic. It was not born as a failure-designed multi-agent CLI.

External signal: Public writing around AI coding workflows increasingly frames git worktrees as the practical substrate for parallel agents. CLI-Anything and adjacent agent-native CLI writing reinforce structured output as baseline, but the stronger opportunity here is recoverable orchestration state, not just --json.

Prior local learning: The create-cli lane already separates Basic CLI, Agent-native CLI, and Facade-backed CLI. The new product should sit firmly in the Agent-native plus Facade-backed lane, with deterministic help, parser acceptance, runtime semantics, and proof that the surfaces cannot drift.

Repo Doctor As The First Command

1

Description: Make doctor the primary read command for the new CLI. It returns the repo's agent-operability map: git root, main worktree, linked worktrees, stale dirs, dirty branches, missing dependencies, contract health, available commands, blocked mutations, and next safe actions.

Axis
Failure and recovery
Basis
direct: AGENTS.md requires maps, invariants, owners, next safe actions, inspectable state, and repair hints. SideQuest already has health-rich worktree reads but no single product-level operational map.
Rationale
Agents need orientation before mutation. A first-class doctor command turns "what state am I in?" into a deterministic contract instead of a chain of ad hoc shell reads.
Downsides
It can sprawl unless v1 names a closed set of checks and explicitly marks deferred checks.
Confidence
90%
Complexity
Medium

Failure Ledger And Continuation Tokens

2

Description: Every failed command writes a small JSONL event with runId, failureId, errorFamily, recoverability, safeToRetrySameInput, idempotencyRisk, and a continuation token. A later agent can run resume <token> or inspect <failureId> to recover the state without rereading the whole terminal transcript.

Axis
Failure and recovery
Basis
direct: skills/agent-reliability-guardrails/references/error-envelope-schema.md already names retry, resume, checkpoint, run correlation, safe retry, idempotency, and action metadata as desirable error fields.
Rationale
This makes failure resumable across context compaction, thread handoff, and side quests. It also turns repeated failures into product data for later hardening.
Downsides
Needs redaction and retention policy from day one. A bad ledger leaks context or becomes another stale truth store.
Confidence
88%
Complexity
Medium

Handoff Packet For Every Work Unit

3

Description: Add handoff as a product primitive, not just prose. It emits a compact packet containing current worktree, branch, dirty state, recent commands, unresolved failures, active docs, next safe actions, and verification status. The packet can be consumed by another agent, a new Codex thread, or a human.

Axis
Multi-agent orchestration state
Basis
reasoned: multi-agent development fails when state is trapped in a single agent's context. A structured packet lets work transfer between agents without trusting memory or chat scrollback.
Rationale
This is the clearest "multi-agent" feature beyond worktrees. It makes agents composable collaborators instead of isolated terminal sessions.
Downsides
Needs tight scope. If it tries to summarize everything, it becomes noisy and expensive.
Confidence
84%
Complexity
Medium

Reconcile Desired Repo State

4

Description: Model repo state declaratively: desired worktrees, workspace render, dependencies, copied config, ignored files, and known safe cleanup. A reconcile command previews drift and applies only safe repairs unless --force is supplied.

Axis
Worktree and workspace truth
Basis
direct: worktree already renders desired workspace output from a registry plus live worktree state and blocks drift. SideQuest already copies config, prunes worktrees, and checks deletion safety.
Rationale
Reconcile unifies scattered repair actions. It lets agents say "restore the repo to the expected operating shape" without manually chaining commands.
Downsides
Needs a careful preview contract so it does not become surprising automation.
Confidence
80%
Complexity
High

SideQuest Logic As Compatibility Source, Not Product Owner

5

Description: Treat SideQuest as a library/source migration pool. Bring across worktree create/list/check/delete/clean/recover/status, but wrap it in a new command contract with stable diagnostic families, explicit no-input behavior, discovery metadata, and repair actions. Keep compatibility shims only long enough to reduce migration risk.

Axis
SideQuest carry-over
Basis
direct: SideQuest command metadata exposes useful verbs, and its cleanup code includes safety checks and backup refs. But its README is stale, and orphan semantics are branch-centric rather than broader repo hygiene.
Rationale
This preserves proven logic without inheriting SideQuest's product ceiling. It also prevents the new CLI from being a renamed wrapper.
Downsides
Migration needs tests that prove old behavior still works where intentionally retained.
Confidence
86%
Complexity
Medium

Worktree Identity And Lease Model

6

Description: Treat each active worktree as an agent work unit with an owner, purpose, lease, dirty state, blockers, and stale-after timestamp. Commands can list leases, renew ownership, detect abandoned work, and refuse destructive cleanup when another agent appears active.

Axis
Multi-agent orchestration state
Basis
external: public AI-worktree workflow writing frames worktrees as the main substrate for parallel coding agents. reasoned: once more than one agent operates, branch/path alone is too weak as identity.
Rationale
Leases make "many agents in one repo" operationally visible. They reduce accidental deletion and give cleanup a principled stale-work signal.
Downsides
Needs to avoid pretending to be a distributed lock. Local leases are advisory unless backed by a shared store.
Confidence
74%
Complexity
High

Contract Simulator And Smoke Corpus

7

Description: Ship a simulator that runs each command through discovery metadata, rendered help, accepted/rejected argv, JSON success, JSON error, no-input behavior, and representative runtime semantics. Keep a smoke corpus of failure fixtures: missing dependency, dirty worktree, stale dir, bad registry, drift block, upstream CLI failure, interrupted run.

Axis
Command contract
Basis
direct: create-cli requires proving discovery metadata, rendered help, parser acceptance, and runtime semantics cannot drift for changed CLI surfaces. agent-reliability-guardrails supplies output and error invariant tests.
Rationale
This turns "agent-native" from aspiration into a regression suite. It also lets worktree and future skills trust the CLI instead of restating its behavior.
Downsides
Less flashy than user-facing commands. Best paired with doctor so value is visible early.
Confidence
82%
Complexity
Medium
