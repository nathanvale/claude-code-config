Ideation: GoF Pressure Lens Skill

Subject: decide whether GoF pattern language deserves its own skill, an ICA overlay, or no new artifact after the claim-safe review pivot.

Basis

Grounding Context

  • skills/skill-feedback/CONTEXT.md defines Pressure pattern: a design-pattern name used only when concrete review pressure has already named a seam.
  • docs/plans/2026-06-13-001-feat-skill-feedback-claim-safe-review-result-v2-plan.md records KTD10: pattern names come from pressure, not cosplay.
  • ica-seam-swarm owns routing, sharding, prompt packaging, synthesis, confidence filtering, and adversary review over existing reports, plans, and ADRs.
  • improve-codebase-architecture owns ICA vocabulary and judgment: Module, Interface, Seam, Adapter, Depth, Leverage, Locality, and deletion test.
  • The review pivot already has earned labels: Facade for ReviewResultData, Adapter for anchor facts, Strategy for claim derivation, and fixed reducer flow for locality.
  • The risk is not missing GoF names. The risk is introducing a second architecture reviewer that hunts patterns before the seam pressure exists.
Decision pressure: preserve No pressure -> no pattern as the gate. Any GoF artifact must translate existing pressure, not discover architecture problems from cold code.
Refactor-discovery addendum: when the input is existing code, run ICA first. Use a solo ICA scan or ICA Candidate Factory to find deepening pressure, then pass only surviving candidates into the GoF lens.

I1. Thin gof-pressure-lens Skill

Conf 86%Cx Low

Create a tiny skill whose job is to translate existing pressure into earned GoF names. Accepted inputs: ICA candidate, ICA adversary review, prototype verdict, plan pressure section, decision log entry, or existing code after an ICA scan has found deepening pressure. Rejected input: cold request to find GoF patterns in code without first identifying seam pressure.

Axis
Ownership boundary
Basis
direct: local context already defines pressure pattern and ICA ownership; reasoned: a thin translator preserves ownership while giving the user the vocabulary they want.
Rationale
This makes GoF useful as naming pressure, not as another architecture review engine.
Downsides
Adds a new invocation surface; needs a hard input gate so agents do not treat it as a pattern finder.

I2. ICA Reference Overlay

Conf 78%Cx Low

Add a small references/gof-pressure-lens.md to the ICA skill family instead of creating a public skill. ICA can load it only when the user explicitly asks for GoF naming after a seam report, plan, or ADR exists.

Axis
Integration path
Basis
direct: ICA already owns prompt mechanics and adversary review over existing artifacts.
Rationale
Lowest surface area. Keeps one review skill and one vocabulary owner.
Downsides
Less discoverable from chat. Users may keep asking for a GoF skill anyway.

I3. Pattern Referee Output Contract

Conf 84%Cx Low

Define the lens by its output, not by its pattern catalog. Every run emits kept names, rejected names, deferred names, seam owner, pressure evidence, deletion-test consequence, and next safe action.

Axis
Output contract
Basis
reasoned: output shape is the strongest guardrail against pattern cosplay because the agent must show why each name survived deletion.
Rationale
The artifact becomes reviewable: a staff engineer can disagree with a kept or rejected label without reverse-engineering the agent's taste.
Downsides
By itself, it is not discoverable. It wants to live inside I1 or I2.
pattern name
  keep   - pressure exists, seam owner named, deletion test passes
  reject - no pressure, weak seam, duplicate ICA term, premature abstraction
  defer  - pressure exists, but second adapter / second use case has not arrived

I4. Anti-Cosplay Input Gate

Conf 82%Cx Low

Make the first step a gate: name the pressure artifact, seam, owner, false-positive prevented, and deletion-test consequence. If any field is absent, stop and route to ICA or decision-mode instead of inventing GoF labels.

Axis
Anti-cosplay
Basis
direct: the plan's GoF section was useful only because claim-safety pressures already existed.
Rationale
The gate makes "No pressure -> no pattern" executable as workflow, not just a slogan.
Downsides
Can feel strict in creative sessions; allow a lightweight "hypothesis only" branch that cannot write durable terms.

I5. ICA Adversary GoF Lane

Conf 72%Cx Medium

Add an optional adversary lane for already-written pattern sections. It attacks whether each GoF label is earned, whether a simpler ICA term is enough, and whether the pattern hides claim-promotion order or readiness facts.

Axis
Ownership boundary
Basis
direct: ICA adversary mode already reviews existing plans and ADRs for weak, unsupported, overfit, duplicate, and not-worth-changing claims.
Rationale
Useful when the user has already drafted pattern language and wants a skeptical pass.
Downsides
Medium complexity because it touches ICA routing and prompts. It is overkill if I1 or I2 handles the need.

I6. No-New-Skill Baseline

Conf 68%Cx Low

Keep the current plan/context language only. Do not author any GoF artifact until a second real case needs pattern translation outside the skill-feedback pivot.

Axis
Integration path
Basis
reasoned: one data point can be local vocabulary, not yet a skill.
Rationale
This is the simplest reliable choice if the team wants zero new surfaces right now.
Downsides
It does not help agents answer the next GoF-lens request consistently; the pattern pressure can drift back into chat memory.

Recommendation

Top Pick

Use I1 as the target shape: a tiny gof-pressure-lens skill with I3's Pattern Referee output and I4's anti-cosplay input gate.

Do not make it a sibling architecture reviewer. Make it a translator that starts only after ICA, a prototype, a plan, or a decision has already exposed concrete pressure.

Give it two explicit entrypoints: Artifact Mode consumes an existing pressure artifact and does not rerun ICA; Code Scan Mode routes to ICA first, then names GoF refactor opportunities only from kept ICA candidates.
