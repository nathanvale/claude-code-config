Grounding Context

The repo already has the pieces for a proof artifact. The generic model in runtime/cli-command-facade/src/station-map.ts projects facade command discovery, a package-owned Branch Station Catalog, and optional evidence into deterministic Station Map JSON. The Storybook work now has two front-door catalogs under skills/storybook/src/front-doors/storybook-doctor/branch-station-catalog.ts and skills/storybook/src/front-doors/storybook-docs-loop/branch-station-catalog.ts.

The boundary matters. Human CLI help comes from command contracts through renderCommandUsage in runtime/cli-command-facade/src/usage.ts. Branch Station catalogs describe declared proof branches: intent, trigger, expected envelope, mutation stance, and evidence status. Generating parser help from those catalogs would blur ownership; generating proof help from Station Maps fits the existing model.

The first Storybook proof concept is unusually good because it has two front doors, two catalogs, real process-boundary tests, and a docs-loop command whose whole purpose is agent continuation. It also exposes a gap: cli-execution-auditor v1 currently searches only for src/branch-station-catalog.ts, while Storybook front-door catalogs live deeper.

External CLI prior art points the same way: frameworks derive ordinary user help from the command model. Clap's Command docs describe defining arguments, subcommands, parser behavior, and help output in one model. Click's Help Pages docs say it automatically generates help pages. Commander.js's README says code describes the CLI while Commander handles parsing, usage errors, and the help system. That makes Branch Station output an adjacent proof surface, not a replacement help engine.

Top conclusion: call the prototype a station proof/help artifact. Keep parser help contract-owned; use Branch Station catalogs to explain what has been proven and what still needs proof.

1

Station Help Artifact Renderer

Agent surface Confidence 88% Complexity Low

Generate a markdown proof/help dossier from Station Maps plus command discovery. The output groups stations by command and shows trigger, expected result, mutation stance, evidence status, and next repair action. It prints to stdout first, then can become a checked generator only after the source and drift check are explicit.

Command contractusage, flags, result contracts
Branch catalogstation intent, trigger, mutation
Evidencecovered, missing, drifted
Proof helpagent-readable station dossier
Basisdirect: projectStationMap already combines discovery, catalog, and evidence into canonical JSON; direct: renderCommandUsage already owns parser help; external: clap, Click, and Commander derive user help from command models.
RationaleThis answers the user's exact "help files from branch-station-catalog" intuition while preserving the repo's contract boundary. It gives agents a map before they touch Storybook docs-loop behavior.
DownsidesIt needs careful naming. Calling it "help" without "station" or "proof" invites misuse as parser help.
2

Catalog-to-Scenario Worklist

Scaffold loop Confidence 84% Complexity Medium

Emit a scenario worklist from the catalog: one row per station id, grouped by command, with expected envelope fields prefilled and blank "fixture setup" and "probe" slots. The worklist can print as markdown or JSON; humans still write package-owned setup and assertions.

Basisdirect: the Branch Station plan requires deriving the integration matrix from the catalog rather than hand-copying rows; direct: the current Storybook docs-loop catalog has 23 station ids that tests must keep aligned.
RationaleThis turns the catalog into the next safe action after planning. It reduces copy drift without producing brittle test source.
DownsidesMedium complexity because it needs a stable row format and a clear rule for optional, skipped, and unreachable stations.
3

Front-door Catalog Locator

Discovery shape Confidence 82% Complexity Medium

Teach the proof renderer, and later the auditor, to discover catalogs under src/front-doors/**/branch-station-catalog.ts as well as the original root path. Storybook becomes the first proof package because it has doctor and docs-loop front doors with separate station maps.

Basisdirect: skills/cli-execution-auditor/src/station-map.ts currently checks only src/branch-station-catalog.ts; direct: Storybook catalogs now live under src/front-doors/storybook-doctor and src/front-doors/storybook-docs-loop.
RationaleThis removes a real adoption obstacle before the model spreads to multi-front-door skills.
DownsidesIt adds path policy. The rule needs to stay narrow enough that unrelated arrays do not become accidental catalogs.
4

Station Evidence Delta Appendix

Adoption cost Confidence 80% Complexity Low

Render a PR-ready appendix from the Station Map: covered stations, missing required stations, drifted stations, skipped or declared-unreachable stations with rationale, and one repair hint per finding. This can be pasted into review notes or emitted by a check without blocking the merge.

Basisdirect: Station Map findings already distinguish missing, drifted, skipped, and declared-unreachable evidence states; direct: the original plan defers mandatory gates until repeated real catches.
RationaleIt gives the team visible value before enforcement. Reviewers can see what proof changed without reading the whole integration suite.
DownsidesLow complexity, but only useful once evidence manifests are consistently produced.
5

Plan-Catalog Sync Lens

Ownership boundary Confidence 74% Complexity Medium

Compare planning-stage Branch Station ids with exported catalog ids and report omissions. For Storybook, this starts with the exported STORYBOOK_DOCS_LOOP_PLANNING_BRANCH_STATION_IDS constant, then can later parse markdown plan tables if that proves worthwhile.

Basisdirect: plans require the first station set to be named before implementation writes the package catalog; direct: Storybook exports the planning station id list beside the docs-loop catalog.
RationaleThis catches the quiet failure where a plan promises a station and implementation momentum drops it.
DownsidesMarkdown plan parsing is likely noisy. Start with exported constants and only parse plans after a second case demands it.
6

Agent Discovery Overlay

Agent surface Confidence 70% Complexity Medium

Add a station-oriented JSON surface that maps command ids to station ids and evidence status. It could be a separate stations --json command or a nonbreaking overlay consumed by agents after commands --json. Keep it distinct from human help.

Basisdirect: Storybook commands already expose commands --json as discovery metadata; direct: Station Map commands already group station ids under command ids.
RationaleThis is the machine-native version of the proof artifact. Agents get a map they can query before selecting tests or editing behavior.
DownsidesIt is a CLI surface, so it needs the full create-cli contract path. Prototype as stdout first.

Rejection Summary

# Idea Reason Rejected
1 Generate real --help pages from Branch Station catalogs Wrong source of truth. Parser help belongs to command contracts; station catalogs prove branch behavior.
2 Generate runnable tests entirely from catalogs Scope overrun. The repo explicitly keeps setup and probe functions out of catalogs.
3 Make Station Maps mandatory gates now Plan conflict. Mandatory gates are deferred until repeated real catches across distinct CLIs.
4 Build a web workbench for station maps Too expensive before the stdout artifact proves value.
5 Embed station catalogs inside command contracts Contradicts the current boundary. Branch Station helpers live beside contracts, not inside CommandFacadeContract.
6 Check in generated Storybook docs output immediately Drift risk without a generated-source header and verification check.
7 Auto-fix missing station evidence Deferred. Findings need to prove stable before repair automation is worth designing.
8 Add trace instrumentation now Adjacent future work. The requested proof concept can run from declared catalogs and evidence first.
Deliberate gap: no UI/workbench survivor. The first useful artifact should be a small stdout renderer because this concept is about source-of-truth boundaries, not presentation polish.
