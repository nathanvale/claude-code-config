Grounding Context

Codebase Context

  • Source idea: ideation #1 in docs/ideation/2026-06-13-repo-workability-improvements-ideation.html — a command that reads diff + recent plan + touched owner paths + skill rules + ignored evidence folders, then emits the next safe check bundle (focused tests, typecheck, lint, doc parse, startup health, fallow, skill-feedback closeout, caveats) with a WHY and a repair hint per check. Confidence 90%, Medium complexity, axis "check orchestration."
  • Repo philosophy it must embody (AGENTS.md Agent-Native Work): give maps, owners, next safe actions, inspectable state; prefer legible tools over prose policy; build mechanical CLI surfaces that emit maps, continuations, and repair hints; keep skills thin — read maps, call owners.
  • The one hard prohibition (AGENTS.md Skill Authoring): never copy contracts, flags, schemas, state machines, or output semantics — name owner paths instead. New/changed CLI surfaces need the facade four-surface proof (discovery metadata + help + parser + runtime can't drift).
  • ~8 check owners exist today: test-runner.sh, context/bun-runner.md, Biome MCP, tsc MCP, fallow, skill-feedback, the create-cli facade proof, and startup health (scripts/agent-instructions.sh / check-workspace-facade-invariants.ts).
  • Proven precedent: mcp-doctor already implements the "doctor" shape (diagnose static config health, emit one-line fixes, exit 2 = the doctor itself could not run). Task Doctor is its working-tree analogue.
  • Known failure mode (memory feedback_prompt_fragments_janitor_tax): validations that need manual upkeep rot; each check must catch real breakage and self-maintain or fail loud.
  • Live evidence (this session): completing plan-003 review, the correct route existed but had to be assembled by hand — the cost was assembly, not capability.
  • Adjacent ideas from the same set: #2 Command Surface Map (a generated index of skill CLIs) and #6 Workability Pulse (the strategic, longitudinal read). Both interlock with Task Doctor.

Topic Axes

  • Route derivation — how it turns diff / plan / touched paths into the check list.
  • Owner coupling — how it calls checks without copying their contracts.
  • Drift resistance — how it stays current as owners and rules change.
  • Output shape & consumption — what it emits and how agent/human act on it.
  • Trigger & lifecycle — when it runs and how it fits the ritual chain.

1.

Owner-declared check verb — the doctor is a thin reducer, and the verbs are the real win

Owner couplingConfidence HighComplexity Medium
Description
Invert the router. Instead of a central command that reads the diff and infers which of the 8 owners apply (which means encoding each owner's applicability logic — copying contracts), each owner declares its own trigger predicate and exposes a uniform check --json verb. Task Doctor degenerates to: collect predicates, evaluate against the diff, emit the union. The "doctor" owns zero check knowledge.
Axis
Owner coupling
Basis
reasoned + direct: Four independent frames (inversion, assumption-breaking, leverage, constraint-flipping) converged on this same move — the strongest signal in the set. Direct: AGENTS.md "keep skills thin: read maps, choose next safe actions, and call owners"; fallow already hand-authors a Skill Route Index (an owner-local predicate table, just in prose). The convergence is the basis: every lens that tried to make the doctor safe landed on "push the knowledge to the owner."
Rationale
This dissolves three risks at once. A central deriver that knows "fallow applies when JS/TS changed" has copied fallow's contract — the one thing AGENTS.md forbids. Owner-declared predicates can't disagree with a route they themselves produced. And the durable asset isn't the router (disposable) — it's N owners each speaking one verb, reusable by CI, the Pulse, ce-code-review, and any future "is this slice safe?" consumer. The doctor is the forcing function; the verbs are the compounding output.
Owner readiness gradient (the implementation map)
The 8 owners are three tiers, and the tier sets the cost. Tier A — already CLI-shaped: test-runner, fallow, skill-feedback have facade-backed runners with command contracts; adding a check/applies verb is cheap and the four-surface proof already guards it. Tier B — MCP-only: Biome and tsc live behind rules/code-quality.md as MCP tools (biome_lintCheck, tsc_check) with no skill CLI. Tier C — script/proof-only: the create-cli facade proof and startup health are a script and a test invariant, with no "owner" object to hang a verb on.
The cleanup makes tier B vanish — and test-runner is its proof
The decisive move (this session's direction): rather than route Task Doctor around the MCP-only checks, promote them into agent-native runners by cloning the proven test-runner shape. test-runner (subcommands run/status/detail; compact/repair/triage/json modes; a command-contract.ts; benchmark + auditor proof) is the reference implementation that format-runner (Biome) and typescript-runner (tsc) get built against — same Agent Runner family, same facade contract, each proven by cli-execution-auditor the way test-runner proves the family. context/bun-runner.md already names them a runner family with MCP as a stopgap ("prefer MCP runners when available"); the cleanup retires that hedge. The work is "clone the test-runner facade twice," not three bespoke CLI builds.
Predicate and verb are separable (rescues tier C)
Idea #1 bundled "declare a predicate" and "expose a check verb," but they're independent. An owner with no CLI (tier C: a script, a test invariant) can still declare its applies-when predicate as static metadata the generator (idea #2) reads, while a tier-A/B runner declares both. The doctor reduces over predicates regardless of whether the owner has an executable verb — so startup-health and the facade proof participate by declaring a path glob, without growing a CLI they don't need.
Downsides
The cleanup is now in scope, so the effort is real and front-loaded: two new runners (format, typescript) cloned and auditor-proven, plus a predicate-declaration convention every owner adopts. Tier-B promotion also means deciding the fate of the existing MCP tools and the rules/code-quality.md "use the MCP runner tools" hard rule — the cleanup must update that rule in lockstep or the two guidance sources contradict. Bigger blast radius than the original "thin reducer" framing implied; better sequenced as its own runner-family cleanup with Task Doctor as the acceptance test, not a side effect.
Confidence
High — raised: the test-runner template + cli-execution-auditor + create-cli facade are all present, so the cleanup path is proven, not speculative
Complexity
Medium for the reducer + tier-A verbs; Medium-High once the format-runner / typescript-runner cleanup is counted (but it clones a working template)

The basis, not the title: every frame that tried to make the doctor safe moved the applicability knowledge out of the center and into the owner.

2.

Generated route table from the Command Surface Map; fail loud on an unmapped touched path

Drift resistanceConfidence HighComplexity Medium
Description
The owner→check→trigger table is generated by scanning owner manifests (SKILL.md frontmatter, facade discovery metadata, the runner table already rendered into AGENTS.md), filtered by the touched paths in the diff — never hand-listed. When an owner is added, regeneration picks it up. When a touched path matches no owner, the generator emits a loud "no check owner for this surface" finding instead of silently skipping it.
Axis
Drift resistance
Basis
direct: ideation #2 (Command Surface Map) is explicitly framed as "a stable input for Task Doctor"; AGENTS.md "Generated files name source; edit source, not output"; memory feedback_prompt_fragments_janitor_tax "each check must catch real breakage and self-maintain." The Bazel/Make affected-targets pattern (external) is the same shape: derive the work-set from a generated reverse-dependency graph, never a hand list.
Rationale
This is the dependency the original idea under-priced. A hand-authored routing table across 8 owners rots exactly like a stale catalog — the janitor-tax trap. Generation makes the Command Surface Map the single chokepoint that the doctor, the Pulse, and CI all read; building the Map once pays off many times. The fail-loud-on-unmapped-path turn converts the most dangerous failure (a false-clean route because coverage has a hole) into a visible finding.
What it indexes (per owner)
One row per command surface: command (e.g. test-runner run), owner-path, contract-id + schema_version, side-effect stance (read / write), execution modes (dry_run / normal), output modes (json / plain), audience (agent / human), help command, and proof file(s). Plus the field idea #1 adds: the applies-when predicate (the path glob / condition that says "this check is relevant to this diff").
What it generates FROM — and the gaps (grounded)
The source already half-exists. 7 skills ship a command-contract.ts (test-runner, fallow, skill-feedback, record-decision, browser-use, classic-cinema, cli-execution-auditor) that already expose contract IDs, schema versions, and side-effect / execution / output / audience metadata — the Map is an aggregator over what these owners already emit, not a fresh registry. The gaps are precise: (1) no index aggregates them today — there's no existing map/catalog file; (2) the tier-B/C owners (Biome, tsc, startup health) have no contract to read until idea #1's cleanup gives them one; (3) SKILL.md frontmatter carries only name + description — the applies-when predicate is a net-new field every owner must declare. So the Map's real cost is "aggregate 7 existing contracts + add the predicate field," scaling to all owners as the runner-family cleanup lands.
How it stays drift-proof
The Map is a generated artifact (AGENTS.md "edit source, not output"), regenerated from owner contracts on demand or in CI. Borrow two proven mechanisms: the existing route-catalog contract-drift extractor (memory feedback_route_catalog_extractor_format) reconciles the Map against the live contracts and fails CI on divergence; and a missing predicate for a registered owner is a generation error, not a silent omission. The Map can't quietly fall out of date because regeneration is mechanical and drift is a test failure.
Bidirectional with idea #1
The two interlock: idea #1 says owners declare a predicate + verb; the Map is where that declaration is aggregated and read. Neither stands alone — #1 without the Map has nowhere to put the declarations; the Map without #1 has nothing meaningful to index beyond what 7 contracts already say. Build them as one move: every owner gains a predicate, the Map aggregates them, the doctor reduces over the Map.
Downsides
Hard sequencing dependency runs both ways now: the Map needs idea #1's predicate field to be useful, and idea #1 needs the Map to read from. Partial coverage during the runner-family cleanup means the Map is incomplete until tier-B/C owners are promoted — the doctor must treat "owner not yet in the Map" as a known gap (the andon turn, idea #6), not a silent skip. Risk of the Map becoming a second source of truth if it ever carries hand-edited rows the contracts don't back — generation-only is the invariant that prevents it.
Confidence
High (conditional on the Map) — raised slightly: 7 owners already emit the source metadata, so the aggregator is grounded, not speculative
Complexity
Medium — Medium-High when the predicate-field rollout across owners is counted
3.

Advisor, never orchestrator — it names checks, it does not run them

Owner couplingConfidence HighComplexity Low
Description
Task Doctor has no --run. It emits the ordered, annotated route — {check, owner-command, why, repair-hint} — and stops. Execution stays with the owners and the agent's existing tool routing (rules/code-quality.md already owns how each check runs and forbids raw bun test). A doctor that can run nothing can't drift into a fragile orchestrator that mirrors 8 owners' flags and output semantics.
Axis
Owner coupling
Basis
direct: AGENTS.md "keep skills thin: read maps, choose next safe actions, and call owners"; rules/code-quality.md already owns check execution. The live evidence isolates the cost: the route had to be assembled by hand — assembly, not execution. The advisor removes 100% of the assembly cost and 0% of the execution coupling.
Rationale
This is the decision that keeps the whole thing thin. The moment the doctor executes, it owns failure handling, retry, timeout, and output parsing for every owner — the universal-orchestrator bloat the source idea warned about, by definition. The value was never in running the checks. A separate one-keystroke "run the bundle" wrapper can consume the doctor's output later; it is not the doctor.
Downsides
Two-step for the user (read route, then run) unless a thin runner wrapper is added. Some will want the doctor to "just do it" — the constraint has to be held deliberately against that pull.
Confidence
High
Complexity
Low (it's a constraint, not code)
4.

Output is the owed-minus-done delta, not a fresh checklist

Output shape & consumptionConfidence MediumComplexity Medium
Description
Instead of "here are 8 things to do," the doctor reads what is already satisfied — an existing skill-feedback closeout receipt for this slice, a fallow audit already run, tests green in the last runner packet — and emits only the unmet delta. The bundle shrinks as you work; an empty bundle means the slice is review-ready. Render it as a single next-safe-action head when the user wants a loop, or the full delta when they want the map.
Axis
Output shape & consumption
Basis
direct: skills/skill-feedback/references/closeout-receipt.md is exactly the "ritual-done" artifact a delta can read; AGENTS.md "after meaningful implementation use fallow; after a material skill run file a skill-feedback closeout"; Nathan/ADHD profile "reduce cognitive load." A fresh full checklist every turn is noise the agent learns to skim.
Rationale
A re-shown full bundle invites cherry-picking and re-running passed checks; a shrinking debt list is a progress signal and a definition-of-done. It reframes the doctor from a reminder into a ledger — which also makes the ADHD-context "where was I in the ritual chain?" question answerable from inspectable state rather than memory.
Downsides
Requires a legible "this ritual is done" signal per owner (a receipt file, a runner packet, a commit convention). Defining that signal is a prerequisite, and a wrong "done" inference is worse than re-listing.
Confidence
Medium
Complexity
Medium
5.

Bind the route at intake; reconcile it post-diff

Trigger & lifecycleConfidence MediumComplexity Medium
Description
"Read the diff after the change" is treated as the moment, but the most expensive failure is discovering at closeout that the task needed a decision log or a facade proof you never set up. Bind the expected check bundle at task intake (from the plan + the owner paths it predicts), then the post-change job is reconciliation: "you committed to these checks; here's what's still red, and here's what the diff added that the plan didn't predict." Intent is an input, not just the diff. This needs a lightweight task handle (base-ref + plan ref) so re-invocation is idempotent against the same task rather than a fresh scan.
Axis
Trigger & lifecycle
Basis
direct: the source idea already lists "recent plan" as an input; fallow already parameterizes on --base-ref HEAD, proving task-scoping is a live primitive. reasoned: a route known only post-diff cannot prevent the missing-ritual class of friction the workability report named — you can't set up a decision log you only learn you owed after the work is done.
Rationale
Shifts the doctor from autopsy to contract. Detecting "you forgot the decision log" up front is a cheaper loop than discovering it at PR review. The task handle is also the precondition that makes the owed-minus-done delta (#4) stable across commits within one task — without it, "current diff" silently drifts as the branch moves.
Downsides
Adds an intake step and a task-handle primitive the repo doesn't have yet. Plans don't always exist (bare-prompt work), so intake-binding must degrade gracefully to diff-only.
Confidence
Medium
Complexity
Medium
6.

Andon cord: get loud on surfaces no owner claims

Drift resistanceConfidence MediumComplexity Low
Description
When the diff touches a path that no owner's predicate claims, the doctor emits a distinct first-class route item — "uncovered: <paths> — no check owner; classify or register one" — rather than producing a short, clean-looking route. It also runs a fast self-check before emitting (every owner it would route to still resolves; mcp-doctor's exit-2 "the doctor itself could not run" pattern), so doctor drift surfaces as the first finding, not a silent wrong answer.
Axis
Drift resistance
Basis
external + direct: Toyota Production System andon cord / poka-yoke — any worker can halt the line at an off-the-known-path condition. Direct: mcp-doctor "exit 2 means the doctor itself could not run"; AGENTS.md "design failures to expose cause, repair path, or human handoff."
Rationale
The dangerous failure of a router is the false-clean — a short route because coverage has a hole, not because the change is safe. The andon turn distinguishes "verified, nothing needed" from "nobody knows," and every run that hits a gap becomes a free coverage audit feeding the Pulse. A self-checking doctor is the janitor-tax discipline applied to the doctor itself.
Downsides
Risk of false alarms on genuinely check-free paths (pure docs, generated output) — needs an explicit "no check needed" classification so the andon doesn't cry wolf.
Confidence
Medium
Complexity
Low
7.

Emit a machine-readable route artifact other tools consume

Output shape & consumptionConfidence MediumComplexity Medium
Description
The derived route is written to a structured task-local artifact (route JSON: each check with owner path, why, repair hint, side-effect stance), and the chat rendering is one consumer of it. The same file then feeds skill-feedback closeout (auto-fill touched_surfaces), the Workability Pulse (signal source), CI (run the same bundle headless), and a drift monitor (did the route the agent ran match the route the doctor recommended?). A per-run ledger of these artifacts becomes the Pulse's longitudinal feed.
Axis
Output shape & consumption
Basis
direct: skill-feedback closeout already takes touched_surfaces (owner paths) and observations; ideation #6 (Workability Pulse) lists "failed checks" as a signal source; AGENTS.md "emit maps, continuations, and repair hints." Reuse the existing route-catalog extractor format (memory feedback_route_catalog_extractor_format) so the artifact inherits an already-paid-for drift test.
Rationale
One structured emission unlocks four downstream consumers without rebuilding any of them — the route stops being a throwaway chat reply and becomes a reusable evidence object. This is the compounding shape choice: the per-task instrument funds the strategic tool (the Pulse) for free.
Downsides
Over-engineering risk if built before any consumer exists — a structured artifact with no reader is speculative. Best sequenced once at least one consumer (closeout auto-fill, or CI) is real.
Confidence
Medium
Complexity

Cross-Cutting Synthesis

The strongest claim in the set

Ideas 1, 2, and 3 are one argument seen from three sides: the real compounding win is not the doctor at all — it is that building it forces every owner to declare a trigger predicate and a uniform check --json verb (1), read through a generated Command Surface Map (2), consumed by a thin advisor that never executes (3). The doctor is the forcing function; the owner contracts and the Map are what actually accumulate. Ideas 4 and 7 then make the doctor's exhaust feed every downstream consumer (closeout, Pulse, CI). The sharpest decision for a brainstorm: does the doctor derive routes (orchestrator, forbidden) or reduce over what owners declare (advisor, sanctioned)? That single fork decides whether this survives six months of owner churn.

Reframe from this session — the runner-family cleanup is the actual project

Once the MCP-only checks (Biome, tsc) are promoted into agent-native runners, Task Doctor stops being the goal and becomes the acceptance test for a uniform Agent Runner family. test-runner is the proven template; format-runner and typescript-runner clone its facade and are proven by cli-execution-auditor — the same way test-runner proves itself today. The sequence inverts: don't build the doctor and route around the ragged owners; level the owners first (every check is an agent-native runner with a declared predicate), and the doctor falls out as a thin reducer with nothing ragged left to special-case. The deliverable is N uniform runners + one generated Map; the doctor is the thing that proves they compose. This also retires the rules/code-quality.md "use the MCP runner tools" hard rule and the context/bun-runner.md "prefer MCP when available" hedge — update both in lockstep with the cleanup.
