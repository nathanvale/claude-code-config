Browser stack · Lesson 1 · ~8 minutes

One envelope, three owners

Mission: judge architectural decisions about your own browser stack instead of rubber-stamping them. This lesson gives you the mental model everything else hangs off.

The one sentence

browser-connect proves the browser and attaches the tool; everything downstream acts only on the Verified Handoff Envelope it mints — nothing else is ever allowed to find Chrome.

It looks like three CLI tools. It's really one assembly line with a single artifact passed along it. Hold onto that and the rest is detail.

mcporter isn't an owner — it's hired plumbing. The adapter's actions (list_pages, take_snapshot) are MCP tools, so something must speak the MCP protocol to it; mcporter is that protocol client, nothing more.

The envelope — the only thing that crosses the seam

{ "status": "ok", "run_id": "…",
  "data": {
    "contract_id": "browser-connect.verified-handoff",   ← browser-use pins this
    "schema_version": "1",                               ← …and this; anything else fails closed
    "outcome": "verified",
    "endpoint":   { "http": "http://127.0.0.1:53412", "ws": "…" },   ← the ONLY endpoint authority
    "attachment": { "adapter_id": "chrome-devtools-mcp",
                    "route": "explicit-cdp",
                    "probe_executable": "/…/chrome-devtools-mcp" },  ← the binary that proved attachment
    "proof": { …warm-chrome provenance… } } }

browser-use enters a session only through this file (--handoff). It never sees a raw port, never guesses 9222, and if the envelope's contract or schema doesn't match its pin, it refuses to parse at all. Consumer parse: skills/browser-use/src/browser-use-discovery.ts · producer: runtime/browser-connect/src/model.ts

Check yourself

1 · Which package implements the “is this really our Chrome?” proof?

warm-chrome owns the proof chain; browser-connect runs it in-process as the front door, and everyone else consumes the result.

2 · What is the only thing browser-use may act on to enter a session?

Envelope in, everything else out. (Fun fact: today's code still reaches the adapter via mcporter's static config — that's exactly the defect the current plan removes.)

3 · The adapter fails to connect. What may browser-use do?

Missing or stale evidence always fails closed — mint a fresh envelope through browser-connect. Adapter fallback after a failure is explicitly forbidden (exit 20 carries no_adapter_fallback).

4 · Why is mcporter in the stack at all?

The adapter's actions are MCP tools over stdio; mcporter is the protocol client. It owns zero browser policy — which is why the current plan can demote it to envelope-fed plumbing.
