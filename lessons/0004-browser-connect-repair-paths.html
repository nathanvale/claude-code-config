Every browser failure needs a safe way forward.

This plan replaces dead-end “inspect something” errors with structured repair instructions an agent can follow without guessing from prose.

Typed evidence → repair policy → one safe continuation → verified Chrome connection

The problem, in junior-dev language

Today, browser-connect can detect failures. Some errors still stop at vague actions such as inspect_listener. The caller learns where to look, but not how to recover.

The plan makes each known failure answer two questions:

  1. What facts caused this failure?
  2. What is the next safe action?

The four-box mental model

1. EvidenceGateways report facts: reason, port, installed version, pin, route, or missing input.
→
2. Policyrepair-path.ts maps typed facts to a recovery posture.
→
3. ProjectionThe CLI converts the policy result into the shared facade envelope.
→
4. DriverAn agent executes the named action or asks the operator to choose.

Key design choice: gateways collect evidence. Policy chooses. CLI formats. Tests prove coverage. Each file gets one job.

Only two legal outcomes

Automatic stage

Emit ordered runtime_actions plus exactly one continuation.next_action_id. Use only safe, non-interactive work.

Operator stage

Emit requires_operator: true plus operator-only choices. Emit no next_action_id.

Safety line: the agent may reuse, launch on a proven-free explicit port, install or safely upgrade an adapter, select a route, and recheck. A human owns process termination, freeing occupied ports, and changing version-pin policy.

Three examples

A better port exists

  1. Check port 9222.
  2. Receive typed reason plus suggestion 9333.
  3. Select use_suggested_port.
  4. Start a fresh call with --port 9333.

The failed call never silently switches ports.

An unknown process owns the port

  1. Reject the listener as unverified.
  2. Do not kill or replace it.
  3. Require operator choice.

Ambiguity fails closed.

An adapter version is wrong

  1. Carry installed and pinned versions as fields.
  2. Select safe upgrade when policy permits.
  3. Require an operator for unsafe pin changes.

No parsing an error sentence for version numbers.

The six implementation units

U1

Build the brain

Add typed repair context and the pure policy. Tests first. Everything else depends on this vocabulary.

U2

Write the repair manual

Create one stable REPAIR.md heading per action. Give each action an owner and stop condition.

U3

Carry the port

Add --port to check, connect, and run. Pass the same validated value through check, launch, recheck, and adapter.

U5

Classify adapters

Return structured install, pin, route, and probe evidence. Distinguish safe repair from policy change.

U4

Wire every error

Project policy through the shared chokepoint. Prove all 13 error stations and all 19 total stations remain covered.

U6

Prove reality

Run safe live smoke checks. Amend the existing architecture decision and package vocabulary.

Why U5 comes before U4: U4 is the integration point. It needs the policy, docs, port evidence, and adapter evidence ready before it can prove every station end to end.

Jargon decoder

Plan wordPlain meaning
Typed contextNamed fields with allowed shapes, rather than facts buried in a sentence.
Pure policyA function that chooses from input data without launching browsers or changing state.
ProjectionFormatting an internal policy result into the public JSON envelope.
ChokepointOne shared function through which all failure envelopes pass.
ExhaustiveEvery allowed failure case is handled; adding one breaks a check until mapped.
Fail closedStop safely when evidence is missing or ambiguous; do not guess a connection.
ProvenanceWhere a fact came from, such as registry pin versus installed adapter version.
StationOne named branch outcome, such as verified, foreign listener, or adapter missing.

What this plan deliberately does not build

  • No generic repair framework.
  • No autonomous multi-step repair engine.
  • No facade schema bump.
  • No weaker Chrome identity proof.
  • No silent fallback port.
  • No automatic process killing or pin-policy changes.

Your 30-second explanation

“Browser-connect already detects failures, but some errors leave agents stuck. This change preserves structured failure facts, runs them through one pure recovery policy, and emits either one safe automatic action or an explicit human choice. It also proves every known failure branch has a repair path without weakening Chrome verification.”

Retrieval checks

Why not choose a repair by reading the error detail?

Prose changes easily and has no enforced shape. Typed fields are stable, validated, and exhaustively handled.

Can automatic alternatives go in continuation choices?

No. Automatic alternatives live in ordered runtime actions with one next action. Choices are operator-only.

Why must a suggested port use a fresh invocation?

It keeps one command bound to one explicit port, prevents hidden behavior changes, and makes the caller's authority inspectable.
