Many adapters can use Chrome 150. They do not all enter the same way.

Chrome is the browser. CDP is the control language. Each adapter chooses a discovery, endpoint, or extension door before it can speak CDP.

AdapterPlaywright, Puppeteer, Browser Use, Selenium, MCP
→
Entry doorUI discovery, explicit endpoint, or extension
→
Chrome 150Targets, tabs, profile state, and CDP sessions

The three doors

1. UI / channel discovery

Reuse the running Chrome profile. Chrome may request consent. No stable port required.

2. Explicit CDP endpoint

Connect to an HTTP or WebSocket address. Widest adapter support. Best for reproducible automation.

3. Browser extension

Attach to selected existing tabs through an installed extension. No public loopback endpoint.

Warm Chrome implication: keep two first-class runtime lanes: current Chrome for UI-aware adapters, and generic CDP for every endpoint-aware adapter. Treat extension attachment as a third, adapter-owned lane.

Multi-agent boundary: multiple clients may attach, but shared transport does not allocate tabs. Give each agent its own target or browser context; otherwise navigation and focus changes can collide.

Retrieval check: which door has the widest compatibility?

An explicit CDP endpoint. UI discovery gives the best current-session experience, but only adapters implementing that discovery handshake can use it.
