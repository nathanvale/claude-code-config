# Issue-to-PR V2 Regression Matrix

Behavior-preservation map for the v1 → v2 refactor (issue #48, U1).

This file is the **single writable target** of the `v2-contract-coverage` seam
in `docs/runbooks/issue-to-pr-v2-refactor/`. It maps current v1 sections and
helper command groups to their planned shadow v2 homes, then records
preservation evidence for the U1 prose-only invariants and deterministic probe
targets.

Authoritative seam: [`docs/runbooks/issue-to-pr-v2-refactor/v2-contract-coverage.md`](../../../docs/runbooks/issue-to-pr-v2-refactor/v2-contract-coverage.md).

## How rows work

| Field | Tables | Meaning |
| --- | --- | --- |
| `id` | all | Stable kebab-case identifier. Used as the dedupe signature for findings against this matrix. |
| `invariant` / `probe target` | prose-only invariants (`invariant`); probe targets (`probe target`); Out-of-scope rows (`invariant`); Removed-by-design rows (`invariant`) | The v1 prose-only invariant or deterministic probe target being mapped. | `v1 source` | all | Where the v1 behavior lives today (file + section anchor or discrete spans). |
| `current contract` | line-map | One-sentence summary of the v1 contract the row maps (what the current major section, helper command group, or carved-out region of v1 actually says). |
| `v2 destination(s)` | line-map; prose-only invariants; probe targets | Where the v1 behavior lands in v2: a reference path, template path, `cli.ts` command family, or explicit `removed-by-design: <reason>`. The Out-of-scope rows table uses `future seam` instead of `v2 destination(s)` because U1 does not own the mapping. |
| `v1 scenario` | prose-only invariants; probe targets | One-sentence description of the v1 behavior that proves the invariant exists. |
| `v2 scenario` | prose-only invariants; probe targets | One-sentence description of the v2 behavior that proves the invariant survived. |
| `probe` | prose-only invariants; probe targets | Manual or automated check that verifies the v2 scenario. `manual` rows go in the manual regression matrix; named `cli.ts ... --json` rows become automated probes in U9. |
| `owner unit` | line-map; prose-only invariants; probe targets | Which v2 implementation unit owns landing the destination (U2 references/templates, U3 modules, U4 CLI, U5 packets, U6 versioning, U7 router, U8 README, U9 probes). | `status` | line-map; prose-only invariants; probe targets | `mapped` (destination confirmed) / `unmapped` (no v2 home yet) / `removed` (intentionally dropped). The Out-of-scope rows table omits `status` because every row in that table is implicitly `closed-not-in-u1-scope` and uses `out-of-scope reason` plus `future seam` columns instead. ## Current contract line-map (U1 scope)

Every current major section and helper command group has one or more v2
destinations (or an explicit removal reason) before extraction begins. A row
with multiple destinations qualifies each destination by the slice of v1
content it owns; see the line-range convention below.

**Line-range convention:** ranges name the section's content boundaries; a row
may include the trailing blank line before the next heading (e.g. `L466-513`
covers Stage 2 prose ending at L512 plus the L513 blank line). **Each
substantive content line belongs to exactly one row.** Structural blank lines
and `---` separators between sections are unassigned by design — they carry
no contract and may sit between adjacent row ranges. Rows may pin discrete
spans (`L1-29, L146-159, L191-238, L415-459`) when a single conceptual
destination spans non-contiguous regions. A row may declare more than one v2
destination when a single coherent v1 unit splits cleanly across v2
destinations (parse vs. emit; Builder rules vs. loop structure); each named
destination must be qualified by the slice of v1 content it owns.
