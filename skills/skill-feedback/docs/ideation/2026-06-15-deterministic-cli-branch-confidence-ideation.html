Ideation: Deterministic CLI Branch Confidence

How to make every CLI we build carry its own durable, testable map of commands, error branches, repair hints, and observability, so confidence comes from contracts and reproducible probes instead of repeated LLM review.

Codebase Context

Existing deterministic spine skills/cli-execution-auditor/src/audit-engine.ts already detects facade-backed CLIs, canonicalizes invocations, runs static checks, runs subprocess surface checks, and emits deterministic findings.
Existing contract vocabulary runtime/cli-command-facade already owns command discovery, result contracts, exit-code floors, action affordances, structured runtime errors, runtime actions, continuations, and diagnostic trails.
Existing process-test pressure scripts/command-entrypoint.integration.test.ts and skills/skill-feedback/src/skill-feedback.test.ts repeat subprocess capture, envelope parsing, failure annotation, and temp-root patterns.
Known honest limit The current auditor proves advertised commands and flags are exercised once. It does not claim every semantic branch is covered. The missing object is a package-owned branch or station oracle.

External grounding supports the split: broad end-to-end tests should stay high-signal rather than exhaustive, branch coverage observes runtime arcs rather than intent, and property-based testing is good at finding input bugs but still needs properties to assert. The repo already has the better starting point: CLI intent is partly declared.

Topic Axes

1. Process-boundary test harness
2. Branch or station inventory
3. Matrix generation and coverage reconciliation
4. Error observability and repair semantics
5. Adoption path across repos

Ranked Ideas

I1 Station Map I2 Branch Catalog I3 Process Harness I4 Matrix Reconciler I5 Gate Ladder I6 Evidence Recorder I7 Branch Workbench
Top pick: combine I1, I2, I3, and I4. That gives a thin shared process harness, a package-owned branch catalog, an auditor-owned station map, and package-local integration tests that prove coverage without centralizing every CLI scenario.

I1.Station Map Contract Layer

Axis: branch inventory Confidence 88% Complexity Medium
Description
Extend the existing auditor with a station-map mode. The map is deterministic JSON describing every known command station: success stations, usage failures, runtime failures, diagnostic branches, recovery choices, continuation paths, and known untestable branches. It is assembled from facade discovery plus package-owned branch declarations.
Basis
direct: the current auditor already has canonical invocation enumeration and deterministic findings; the facade already has runtime envelope fields for errors, actions, continuations, and diagnostics.
Rationale
This is the missing middle object between command contracts and tests. A station map lets agents ask "what branches exist?" before asking "which tests cover them?"
Downsides
It needs careful language. It should claim declared branch coverage, not whole-program branch completeness.

I2.Package-Owned Branch Catalog

Axis: repair semantics Confidence 85% Complexity Medium
Description
Give each CLI a typed branch catalog near its command contract. Each branch has an id, owning command, setup recipe, argv, expected exit code, expected envelope status, expected error code or action, expected recoverability, optional diagnostic trail, and coverage classification.
Basis
direct: the facade contract deliberately keeps package result vocabulary package-owned. Branch semantics are the same kind of package vocabulary.
Rationale
The branch catalog supplies the intent oracle. Static analysis can see code paths, but only the package can say that protected_branch should expose a failure ref, recovery choice, and no destructive mutation.
Downsides
Authors must keep catalog entries real. Mitigate with generated maps, auditor findings, and package-local integration tests.

I3.Shared CLI Process Test Harness

Axis: process harness Confidence 92% Complexity Low
Description
Extract process testing helpers into @side-quest/cli-command-facade/testing: run a CLI subprocess with timeout, capture streams, annotate failures, parse JSON envelopes, assert ok/error status, preserve temp roots on failure, and run labeled surface cases.
Basis
direct: the exact helper pattern now repeats between the root command-entrypoint integration test and skill-feedback's CLI process tests.
Rationale
This is the first implementation slice because it is already earned by two consumers and lowers the cost of every later station-map test.
Downsides
Keep it generic. Temp git seeding and package-specific assertions stay with the owning tests.

I4.Matrix Generator And Coverage Reconciler

Axis: matrix reconciliation Confidence 82% Complexity Medium
Description
Use the station map to derive test rows. Package tests can import the generated row model or the auditor can compare observed test receipts against station ids. Missing required stations become deterministic findings.
Basis
direct: the current auditor already turns clauses into findings; command-entrypoint tests already hand-build a runtime JSON command matrix.
Rationale
It turns "I think we tested the branches" into a mechanical statement: every required station is covered, intentionally skipped, or reported.
Downsides
Generated test files can become awkward. Prefer generated data or reports first; write source tests by hand against the shared helper until the shape stabilizes.

I5.Auditor-As-Gate Ladder

Axis: adoption Confidence 80% Complexity Medium
Description
Promote confidence in stages: shared harness, package-local branch catalog, station-map report, missing-coverage findings, fixture oracle, then enforcement after repeated real catches across repos.
Basis
direct: the existing CLI auditor plan already split opt-in v1 from a later mandatory gate and named a real-catch threshold.
Rationale
This keeps the pattern from becoming ceremony before it proves value. Each rung earns the next one with evidence.
Downsides
Slower than making it mandatory immediately, but less likely to create noisy gates that people route around.

I6.Runtime Evidence Recorder

Axis: matrix reconciliation Confidence 74% Complexity Medium
Description
Let integration tests emit stable station receipts during execution: station id, argv, exit code, envelope status, error code, action id, and sanitized diagnostics. The auditor compares receipts to station-map requirements.
Basis
external: coverage tools can record runtime branch arcs, but arcs alone do not encode domain meaning. Receipts add the semantic label that agents and humans need.
Rationale
This creates a bridge between "the test ran" and "the declared error station was observed." It is especially useful when one test covers several stations.
Downsides
Receipt storage can become generated-output noise. Start with in-memory receipts inside a test run before writing durable files.

I7.Branch Workbench Report

Axis: repair semantics Confidence 72% Complexity Low
Description
Render an HTML and JSON report showing every station grouped by command, with expected repair hints, observed test status, skipped rationale, drift findings, and next safe action.
Basis
reasoned: a station map is useful to machines, but the pattern spreads across repos only if maintainers can inspect and trust it quickly.
Rationale
The report turns invisible confidence work into an inspectable artifact. It is also the handoff surface when a coverage gap is intentional.
Downsides
Report polish can distract from the contract. Keep JSON canonical first, HTML as a reader view.
