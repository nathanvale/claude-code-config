Ideation: Skill Feedback Review Pivot

Angles for the pivot from category-first review toward evidence tiers, exact ledger anchors, and runtime-aware observability across Codex and Claude Code.

Date: 2026-06-13 Topic: skill-feedback-review-pivot Mode: repo-grounded Raw ideas: 40 Survivors: 7

Grounding Context

Current pivot

Decision 20 moves active v2 work to a closeout-first anchor ledger. Driver closeouts can build review value now. Trusted skill identity stays a separate readiness claim.

Key invariant

review_unit_key answers same-run coalescing. ledger_anchor_key answers recurring stable surface. Evidence source, runtime, tier, friction, open reason, report id, and skill_run_id do not form the ledger key.

Runtime split

Codex Stop is Stop-detected turn evidence. Claude Code can reach Stop-detected skill when supported evidence names a completed skill run. Neither proves Codex trusted skill identity.

Implementation reality

The current code is still v1-shaped: ReviewResultData has capture_readiness, open_items, no ledger entries, no evidence tiers, and no weak-anchor fields yet.

External pattern

OpenTelemetry, OpenInference, incident review, trace context, and provenance systems all point in the same direction: trace/provenance first, categories later.

Product stance

The artifact is the instrument. Prefer mutation-free review output and inspectable local state before dashboards, background automation, or new category models.

1 Replayable Ledger Reducer With Golden Vectors

Axis: Contract migration Confidence: 91% Complexity: Medium

Description: Build v2 as a pure reducer over normalized reports: review units in, ledger entries plus weak-anchor telemetry out. Pair it with golden vectors that prove key behavior before rendering gets persuasive. JSON, plain output, tests, and future category proposals consume the same reducer.

Basis: direct: the v2 plan requires review-unit keys, ledger anchor keys, exact grouping, weak-anchor reasons, and renderer vocabulary in the command contract; the current code still exposes only v1-shaped review output.

Rationale: This is the smallest structural move that makes "simple and reliable" true. One reducer becomes the source of truth instead of letting plain output, JSON, and tests each reinterpret reports.

Downsides: Requires disciplined contract-first implementation. It may feel slower than adding a renderer, but it prevents the renderer from inventing behavior.

2 Two Keys, Two Claims

Axis: Anchor reliability Confidence: 90% Complexity: Low

Description: Make the mental model explicit everywhere: review_unit_key means "same run"; ledger_anchor_key means "same stable surface." Neither key is allowed to imply the other's claim. This should appear in contract names, tests, plain labels, and docs.

Basis: direct: the plan says same ledger_anchor_key alone never upgrades to corroborated, and skill_run_id is excluded from the ledger key.

Rationale: This catches the most tempting false merge in the system. It is also a teachable phrase that future agents can remember.

Downsides: Naming has to stay strict. If later code aliases the keys or hides them behind one helper, the distinction will decay.

3 Claim Budget Badges

Axis: Runtime identity boundary Confidence: 86% Complexity: Medium

Description: Render each ledger entry with the claims it is allowed to make: repeated anchor, mixed runtime evidence, same trusted run, or trusted engine identity. Treat evidence tiers as the underlying data, but give humans and agents claim-scoped wording they can safely repeat.

Basis: direct: Decision 20 preserves Codex Stop as runtime evidence, Claude Stop-detected skill as stronger runtime-specific evidence, and Trusted skill identity as a separate gated claim. external: digital forensics and SLSA-style provenance separate evidence custody from claim strength.

Rationale: Tier enums are precise but easy to overread. Claim badges turn tier state into safe language and make false readiness harder to create.

Downsides: Adds renderer vocabulary. The badges must be generated from contract-owned states, not ad hoc copy.

4 Weak-Anchor Quarantine

Axis: Future-category pressure valve Confidence: 84% Complexity: Medium

Description: Make weak anchors a named lane rather than leftovers. Label-only, missing, out-of-repo, or unverifiable anchors stay standalone. They get a weak-anchor reason, attempted target, source mix, open-signal facets, and anchor-miss telemetry outside merged ledger counts.

Basis: direct: the active plan keeps weak anchors standalone and emits telemetry without merging it. external: flaky-test quarantine preserves signal while protecting the main result set.

Rationale: This keeps the no-false-merge rule while still learning from messy evidence. It is the pressure valve that lets v2 stay simple without becoming blind.

Downsides: Needs careful plain output so the quarantine lane does not become the loudest section.

5 Readiness Ladder And Stop Observability Panel

Axis: Runtime identity boundary Confidence: 82% Complexity: Medium

Description: Replace one Codex gate with ladder rungs: runtime capture observed, hook config trusted, approval observable or attested, close detection present, shared trusted run id, trusted skill identity proven. A Stop observability panel shows Codex Stop-detected turn counts, Claude Stop-detected skill counts, active hook source-set state, and blocked identity reasons.

Basis: direct: current readiness still couples implementation readiness to trusted Codex Stop identity, while the active plan separates runtime capture, trusted identity, and daily pilot. external: trace and observability systems show partial progress as explicit state rather than one binary flag.

Rationale: This lets Codex Stop become useful evidence without pretending it proves skill identity. It also keeps Claude Code's stronger Stop evidence visible without polluting Codex readiness.

Downsides: More states mean more renderer responsibility. The ladder must stay sparse and test-backed.

6 Coverage First, Anchor Second, Exceptions Last

Axis: Review output workflow Confidence: 78% Complexity: Low

Description: Make plain review follow a fixed reading order: coverage and no-action health first, readiness boundaries second, anchor ledger third, weak-anchor lane fourth, open exceptions last. Open reasons remain facets inside entries, not the organizing principle.

Basis: direct: v1 review already leads with coverage, opens only high-signal items, and stays mutation-free. The v2 plan appends ledger detail after existing triage and excludes open reason from the ledger key.

Rationale: Output order is the product doctrine in miniature. This keeps human reading simple and prevents v1 open reasons from sneaking back into category-like grouping.

Downsides: Could bury urgent exceptions if the first sections grow too long. Needs length caps and terse plain rendering.

7 Category Pressure Valve

Axis: Future-category pressure valve Confidence: 76% Complexity: Medium

Description: Assume v2 never gets product-native categories unless ledger data earns them. Review can emit a non-grouping category-pressure section or separate proposal artifact that cites repeated strong anchors, repeated weak-anchor telemetry, examples, and the decision needed to accept a future category view.

Basis: direct: Decision 20 removes category-first scope but leaves future category work possible only after real ledger data proves the need. external: library authority control separates stable item records from evolving subject headings.

Rationale: This makes "not now" durable. It gives category pressure somewhere to go without letting it leak back into v2 grouping.

Downsides: This is mostly a follow-up mechanism. It should not distract from shipping the reducer and golden vectors first.

Rejection Summary

Cut Idea Reason Rejected
Anchor Compiler, Not Classifier Folded into the reducer and golden vectors. As a standalone idea it is useful, but weaker than the test-backed implementation shape.
Snap-To-Road Anchor Canonicalizer Rejected because the metaphor can imply fuzzy snapping. V2 needs deterministic repo-path canonicalization only.
Trace-First Review Unit Rejected because it can over-center runtime traces and weaken the closeout-first pivot.
No-Action As A First-Class Result Sound but already covered by the review-output workflow. It does not need a separate ideation direction.
Contract Stratigraphy Guard Useful but belongs inside contract migration and self-diagnosis, not as a standalone product direction.
Accepted Proof Upgrade Path Valid but too future-facing for the immediate pivot. Keep it as a later extension after the reducer exists.
Runtime Identity Ladder Lints Sound but folded into Readiness Ladder and Claim Budget Badges.
