browser-use as a facade · powered by Chrome DevTools for Agents 1.0

One stable interface, many swappable browser engines. Ideation on what the facade — and Chrome's new release — buys us.

2026-06-12 repo-grounded · rev 2 (facade frame) 10 survivors · ~45 raw 5 axes · all covered weight: lean internals, rich interface
The product is the facade. browser-use exposes one interface — operate / observe / verify — and runs it on interchangeable engines underneath (chrome-devtools today; playwright and agent-browser staged). The caller never names an engine. Chrome DevTools for Agents 1.0 is not a reason to collapse this — it's the strongest implementation to sit behind it, and the yardstick for the facade's capability vocabulary. So the Router, manifests, and adapter-proof are not redundancy: they're the facade's machinery, and they earn their keep the moment N>1 is the plan. The subtraction angle survives, correctly scoped: each adapter should map to Chrome's native surface rather than hand-build it. The exciting angle — your explicit ask — is what swappability itself buys: cross-engine verification, graceful failover, cost routing, vendor-independence, and a correctness oracle no single engine can offer.

Ranked ideas

★ 1

Differential cross-engine verification — the correctness oracle

ADDSwappability dividendsConf HighCx M

Run the same observe/verify through two engines and diff the results. Agreement is independent ground truth; disagreement localizes the lie (flaky page, race, or adapter bug). This capability cannot exist with N=1 — it is the purest answer to "what does swappability buy." Surfaced independently in 4 of 5 frames.

Scenario: agent submits a payment form. Playwright reports "click succeeded, navigated." chrome-devtools sees a swallowed 402 in the network panel and zero DOM change. The facade flags "action claimed success, observation contradicts," refuses closeout, and attaches both verdicts.

Basis · direct + reasoned

Differential testing (csmith for compilers, SQLite-vs-Postgres oracles): two independent implementations disagreeing is a bug signal needing no golden output. Requires the floor contract to guarantee comparable output shapes.

Why it matters

A single engine verifying itself is a tautology. Only N>1 turns verify from self-report into measurement. Thinnest form: a --differential flag on the test-runner, not a standing service.

Meeting test: "Can one engine catch another engine lying about success?"

★ 2

Graceful degradation / fallback chains (LiteLLM-style)

ADDSwappability dividendsConf HighCx M

Declare an ordered engine preference; the Router fails over transparently on capability miss or attachment failure, and the diagnostic envelope carries a servedBy field. When the preferred engine drops mid-run, fall to the next engine that satisfies the subset of capabilities the task still needs — not the full ceiling.

Scenario: a 20-step flow is on step 12 when Chrome 147 breaks --autoConnect and chrome-devtools can't bind. The remaining steps need only click/type/assert, so the facade hot-swaps to playwright, annotates "steps 12–20 served by fallback," and finishes instead of dying.

Basis · reasoned + direct

LiteLLM/OpenRouter fallback chains — ordered provider list, transparent failover, response field naming who served. Maps onto ADR 0012/0013 evidence-first routing, which already does attachment-proof.

Why it matters

Single-engine automation is a single point of failure. Swappability converts an upstream outage into a degraded-but-complete run. This is vendor-independence made operational.

Meeting test: "When the best engine dies mid-task, does the task still finish — and does the caller see which engine answered?"

3

Capability-addressed calls + a three-verb floor

ADDCapability negotiationConf HighCx M

Callers request a capability (verify.network.idle, observe.perf.trace) — the engine name never appears in caller code. Lock the facade to a guaranteed floor (operate/observe/verify every engine must satisfy) and a negotiated ceiling (heap/lighthouse only some engines reach). An engine that can't do the floor isn't selectable; ceiling misses return a typed capability-unavailable with the degradation path — never a silent fake.

Basis · direct

Grounding: caller requests capability not engine; scope→capability resolver is facade-level. ADR 0012/0013 exists precisely to reject engine-coupled universal APIs that fake uniformity. OpenGL core-profile + extension-query precedent.

Why it matters

This is the contract that makes everything else possible — wiring playwright tomorrow touches zero callers only if no caller ever named chrome-devtools. The negotiation IS the value, not a tax.

Meeting test: "Show me one caller that names 'chrome-devtools.' If you can't, the facade is real."

★ 4

Verify-after-operate lives in the facade, once

ADDFacade-level moatConf HighCx M

Post-action verification (did the click change state? did navigation settle?) is implemented once at the facade and wraps every adapter's operate. Each engine only maps "how do I read state after acting" using its native read tools; the verdict logic is shared. Chrome's #1 documented gap becomes a solved facade feature every engine inherits.

Basis · direct

Chrome ships no post-action verification (named gap). It's engine-agnostic by nature. verify is already one of the three facade verbs.

Why it matters

Solving Chrome's biggest gap once for N engines is a moat no single-engine MCP can match. Add engine #4 → it inherits the closed feedback loop for free. Lean: a wrapper over engine read tools, not a subsystem.

Meeting test: "Why does Playwright get post-action verification for free when we never wrote verification code for it?"

5

Codec-container split: facade owns the moat, adapters own only the codec

SUBTRACTFacade-level moatConf HighCx S

An MP4 container handles timing/metadata/muxing identically regardless of codec. Make that split structural: verify, redaction, auth-handoff, Warm Chrome, and selected-target state live once in the facade "container"; every adapter implements only the thin "codec" (raw browser ops against its engine). No adapter ever hand-builds redaction or verification — they get it free by sitting inside the container.

Basis · reasoned + direct

Video codec containers: container owns muxing uniformly, codec owns frame decode. Grounding already names verify/redact/auth/state as engine-agnostic facade-level layers.

Why it matters

Guarantees every future engine inherits the moat and can't drift on it. "Add an engine" becomes cheap because the engine only writes the codec. This is the structural rule that keeps adapters lean.

Meeting test: "When we wire playwright, does it write its own verify+redact, or inherit the facade's?"

★ 6

Record-at-facade, replay-anywhere

ADDSwappability dividendsConf MedCx M

Capture intent at the interface level (operate "click Submit", verify "toast shown") — not engine-specific selectors or CDP calls. A recording made today on chrome-devtools replays tomorrow on playwright unchanged, because intent (not mechanics) was captured. Doubles as the playwright-wiring acceptance test: if the Chrome recording replays clean on playwright, the facade is genuinely engine-neutral.

Scenario: a flaky CI test recorded against chrome-devtools survives Chrome 147 breaking the engine — the same transcript replays on playwright with zero re-authoring. The test corpus outlives any single engine.

Basis · direct + reasoned

Stripe idempotency keys / payment intents: capturing intent at the gateway makes execution processor-independent. Engine-neutral only because the floor contract (idea 3) is engine-agnostic — downstream of it.

Why it matters

Recordings tied to one engine die with it; intent-level capture makes the corpus durable. Revives the deferred record/replay thesis at near-zero cost — a transcript file, not a deterministic walker. Carry forward why replay was deferred (LLM variance) before building execution.

Meeting test: "Does a recording survive swapping the engine underneath it?"

7

Adapters map to Chrome's native verbs — never rebuild them

SUBTRACTPer-adapter subtractionConf HighCx S

The correctly-scoped subtraction. For any capability Chrome ships natively (perf-trace, lighthouse, console, network, heap, emulation), the chrome-devtools adapter is a thin map onto the native tool — never a re-implementation. The 7 unwired manifest caps map ~1:1 onto Chrome's categories. Rule: if the engine ships the verb, the adapter binds; it only hand-builds the floor verbs the engine lacks. Defer batching to evaluate_script and token budget to --slim.

Basis · direct

CUPS print drivers: thin glue over native device capability, never reimplementing the device's functions. chrome-devtools-mcp = 44 tools; transport is already a thin ${adapter}.verb switch.

Why it matters

Keeps each adapter steipete-lean exactly where lean applies (internals). The interface stays rich; the adapter is the thinnest map to native power, so adding engines stays cheap.

Meeting test: "For each Chrome tool we expose, did we map it or rebuild it? Any rebuild is a bug."

8

Data-driven capability registry + live-query Chrome's tool list

SUBTRACTCapability negotiationConf MedCx M

termcap/terminfo stores capabilities in a queried database, not in code; absence is the honest signal. Replace the 3 hand-declared manifests with one flat registry (cap-id → engines that satisfy it) the Router reads. For chrome-devtools specifically, derive caps from a live query against Chrome's exposed tool list at attach time instead of a frozen snapshot — killing the drift that appears the moment Chrome ships tool 45.

Basis · reasoned + direct

termcap/terminfo capability DB with graceful absence. Grounding: manifests hand-declare 10 caps, 7 unwired; a hand-maintained snapshot is guaranteed to lie. ADR 0012/0013 was built to prevent false-capability claims.

Why it matters

Self-truing manifest kills a whole class of false-capability bugs. Adding an engine = adding rows, not editing prose in three files. Keeps the negotiation contract honest as engines evolve.

Meeting test: "Can the chrome-devtools cap list be a live query at attach, instead of a snapshot we edit by hand?"

9

Facade-level Warm Chrome + auth/MFA handoff, shared across CDP engines

ADDFacade-level moatConf HighCx S

Warm Chrome (dedicated debug profile + manual pre-auth) becomes a declared facade-level precondition that any CDP-speaking adapter consumes — chrome-devtools and playwright-cdp both attach to the same warmed session instead of each re-solving the Chrome-136 block. Auth-wall/MFA handoff (pause → human → resume) is a facade lifecycle event every engine raises identically. Chrome 1.0 validates this: its "session hand-off" reality is Warm Chrome.

Basis · direct

ADR 0006 Warm Chrome shared precondition; real profile blocked since Chrome 136, --autoConnect flaky (#1830). MFA/auth walls are named Chrome gaps, none engine-specific.

Why it matters

Three CDP adapters would otherwise re-solve the same auth/attach nightmare three times. Solve it once; a new engine inherits the only reliable attach path by declaring it consumes the precondition.

Meeting test: "What does playwright-cdp need for reliable Chrome attach? Declare it consumes Warm Chrome — the facade already owns resolution."

10

Engine onboarding lifecycle: known → provable → mapped → selectable

ADDCapability negotiationConf MedCx S

Name the four gates a new engine passes: known (registered), provable (passes adapter-proof attachment), mapped (manifest declares floor+ceiling against the capability vocabulary), selectable (rubric-evaluated, wired end-to-end). playwright and agent-browser sit at mapped-but-not-selectable — the lifecycle names exactly what wiring playwright requires next, turning "dead adapters" into a legible pipeline.

Basis · direct

Grounding names the lifecycle; 2026-06-11 agent-cli-evaluation is the lane that decides which engines become adapters (playwright already rubric-evaluated). Chrome DvA 1.0 enters as a rubric pass, not a redesign.

Why it matters

Makes the multi-engine roadmap explicit and removes the "is this cruft?" ambiguity that derailed the first ideation pass. Everyone knows the next move.

Meeting test: "Where's playwright in the lifecycle?" → "Mapped, not selectable — needs end-to-end wiring."

Recommendation

Foundation first: lock idea 3 (capability-addressed floor/ceiling contract) and idea 5 (codec-container split) — these define what the facade is and make everything downstream cheap. Then idea 7 (map the chrome-devtools adapter to Chrome's native surface) closes the 7 unwired caps almost for free and proves the lean-adapter rule. Idea 4 (facade verify) + idea 9 (shared Warm Chrome/auth) build the moat every engine inherits. Then wire playwright (idea 10) — the moment a second engine is live, the dividends (★ ideas 1, 2, 6) become real, not theoretical. Treat idea 1 (differential oracle) as the flagship demonstration that swappability is the product.

On Chrome 1.0 specifically: adopt it as the best current engine and the capability yardstick — map to its 44 tools, defer budget to --slim, ignore WebMCP until 2027, and never let its "session hand-off" marketing tempt anyone to delete Warm Chrome.
